## 한 줄 결론

**현재 데이터 규모에서는 pandas가 빠르다. 전환 임계는 약 2,000만~5,000만 행이고, 우리 최대 테이블은 1,620만 행이라 아직 그 아래다.**
단 메모리는 이야기가 다르다 — Spark는 전 구간 2.5~8.7GB로 평평하고 pandas는 51.8GB까지 올라간다.

## 1. 어떤 실험을 했나

### 가설

"집계 데이터는 작아서 그대로 쓰고, 원본 로그·스트림·조합 폭발 계산에만 분산을 썼다"(`AI/README.md` 3절)는
설계 전제가 **실제 우리 데이터에서 수치로 성립하는지**, 그리고 성립한다면 **몇 행부터 뒤집히는지** 확인한다.

### 비교 대상 — 실제 파이프라인의 무거운 연산 3종

파이프라인에서 실제로 무거운 패턴을 그대로 옮겼다. 저장소 규약대로 시차 피처는 위치 shift가 아니라
**날짜+슬롯 키 조인**으로 만든다(빠진 날이 있어도 이전 행을 끌어오지 않기 위함).

| OP | 이름 | 내용 | 입력 파일 | 원본 행수 |
| --- | --- | --- | --- | --- |
| A | `panel_join` | (역·슬롯·요일유형) 평균 lookup → 잔차 → 날짜 키 조인으로 lag1d/lag7d 잔차 생성 | `data/CROWD/processed/crowd_panel_2024_2025.parquet` | 3,987,000 |
| B | `ratio_agg` | (역·슬롯·요일유형·방향) mean·count·분위수(0.5/0.9) 집계 | `data/CROWD/processed/crowd_congestion_label_calibrated_2024_2026.parquet` | 16,195,530 |
| C | `long_pivot` | 롱포맷(승차/하차) → 와이드 pivot | `data/CROWD/interim/crowd_daily_ridership_long.parquet` | 11,959,400 |

OP-A는 89번에서 "세트당 4~5분 중 대부분이 400만 행 조인"으로 지목됐던 바로 그 병목이다.

### 스케일 증폭 방식

원본을 그대로 N번 쌓으면 조인·집계 키가 중복돼 부하가 실제로 늘지 않는다(lookup 평균이 그대로 유지되고
lag 조인이 자기 자신과만 매칭된다). 그래서 **복제본마다 날짜를 3년씩 밀어** 각 복제본이 독립된 기간처럼
동작하게 했다. 1x / 4x / 16x / 64x 네 단계.

### 측정 항목 (`spark-comparison-checklist.md` 항목을 그대로 따름)

- **정확성 우선** — 속도를 재기 전에 1x에서 pandas·Spark 결과가 수치적으로 같은지부터 확인
- `wall_seconds` = 읽기 + 증폭 + 연산 (엔진 간 공정 비교를 위해 총합을 쓴다. Spark는 lazy라
  읽기·증폭 비용이 연산 단계로 흘러들어간다)
- `peak_rss_mb` — 프로세스 트리 피크 RSS. psutil로 0.2초 간격 샘플링, **Spark JVM 자식 프로세스 포함**
- SparkSession(JVM) 기동 시간 — 하루 1회 배치에서는 이 고정비가 그대로 지연에 얹힌다

## 2. 결과

### 2.1 정확성 — 세 OP 모두 일치 (속도 비교의 전제)

| OP | 행수 일치 | 최대 절대오차 | 판정 |
| --- | --- | --- | --- |
| A `panel_join` | 3,987,000 = 3,987,000 | **0.0** (완전 일치) | ok |
| B `ratio_agg` | 44,928 = 44,928 | 2.7e-12 (mean), 4.5e-13 (p90) | ok |
| C `long_pivot` | 5,979,700 = 5,979,700 | **0.0** (완전 일치) | ok |

허용 오차 1e-6 대비 여섯 자릿수 이상 여유. NULL 위치 불일치도 0건.
**로직이 같다는 게 확인됐으므로 아래 속도 차이는 구현 차이가 아니라 엔진 차이다.**

### 2.2 처리 시간 — 손익분기점은 2,000만~5,000만 행

`wall_seconds` 기준. 비율은 `Spark ÷ pandas` — **1보다 작으면 Spark 승**.

| OP | 배수 | 입력 행수 | pandas | Spark | 비율 | 승자 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| A `panel_join` | 1x | 3,987,000 | **2.8초** | 7.3초 | 2.61 | pandas 2.6배 |
| | 4x | 15,948,000 | **14.0초** | 17.0초 | 1.21 | pandas 1.2배 |
| | 16x | 63,792,000 | 62.8초 | **49.3초** | 0.79 | Spark 1.3배 |
| | 64x | 255,168,000 | 423.9초 | **153.9초** | 0.36 | Spark 2.8배 |
| B `ratio_agg` | 1x | 16,195,530 | **5.1초** | 6.7초 | 1.31 | pandas 1.3배 |
| | 4x | 64,782,120 | 22.5초 | **11.3초** | 0.50 | Spark 2.0배 |
| | 16x | 259,128,480 | 99.0초 | **27.0초** | 0.27 | Spark 3.7배 |
| | 64x | 1,036,513,920 | 747.3초 | **91.8초** | 0.12 | Spark 8.1배 |
| C `long_pivot` | 1x | 11,959,400 | **6.1초** | 7.6초 | 1.25 | pandas 1.3배 |
| | 4x | 47,837,600 | 28.1초 | **12.5초** | 0.44 | Spark 2.2배 |
| | 16x | 191,350,400 | 114.1초 | **34.2초** | 0.30 | Spark 3.3배 |
| | 64x | 765,401,600 | 중단(§2.4) | **114.4초** | — | Spark만 완주 |

**교차 지점**: A는 1,600만~6,400만 행 사이, B는 1,620만~6,480만 행 사이, C는 1,200만~4,800만 행 사이.
세 OP이 서로 다른 연산(조인·집계·pivot)인데도 **일관되게 2,000만~5,000만 행 구간에서 뒤집힌다.**

### 2.3 메모리 — 여기서는 Spark가 전 구간 우세

`peak_rss_mb` (GB 환산).

| OP | 배수 | pandas | Spark |
| --- | ---: | ---: | ---: |
| A | 1x → 64x | 1.1GB → **50.2GB** | 2.4GB → **8.6GB** |
| B | 1x → 64x | 3.2GB → **51.8GB** | 1.7GB → **2.7GB** |
| C | 1x → 64x | 2.3GB → 중단 시점 49.2GB | 2.4GB → **8.8GB** |

pandas 피크는 데이터 크기에 정비례해 올라가고, **Spark는 64배 데이터에도 2.7~8.6GB로 평평하다**
(드라이버 힙 8GB 상한 안에서 디스크 스필로 처리). 10억 행 집계(B 64x)에서 pandas 51.8GB vs Spark 2.7GB —
**19배 차이**. 이게 Spark가 사는 진짜 이유이지 속도가 아니다.

### 2.4 pandas가 완주하지 못한 지점

- **C 64x (7.65억 행 pivot)**: pandas가 49.2GB까지 올라가 시스템 여유 메모리가 1.9GB로 떨어졌다.
  OS OOM killer를 기다리지 않고 **작업자가 개입해 종료**했다(`status: crashed`, returncode -1).
  자연 OOM이 아니라 사람이 끊은 것이므로 "pandas가 죽는 정확한 한계점"은 미측정.
  **같은 셀을 Spark는 114.4초·피크 8.8GB로 완주했다** — 이 비교가 이번 실험에서 가장 선명한 한 장면이다.
- A 64x(2.55억 행)와 B 64x(10.4억 행)는 pandas가 **완주는 했다** — 다만 각각 50.2GB, 51.8GB를 쓰고
  423.9초·747.3초가 걸렸다. 63.5GB 머신에서 이 정도면 다른 작업을 같이 못 돌린다.

### 2.5 SparkSession 고정비 — 현 규모에서는 이게 결정타

**JVM 기동에 7.03초.** 현재 실제 데이터로 세 OP을 pandas로 다 돌리면 합계 14.0초다(2.8+5.1+6.1).
즉 지금 규모에서 Spark로 바꾸면 **일하기도 전에 전체 작업 시간의 50%를 세션 기동에 쓴다.**

### 2.6 병렬도·셔플 파티션

"Spark가 느린 건 튜닝을 안 해서 아닌가"를 차단하려고, 가장 무거운 64x 구간에서 세 가지 설정을 따로 쟀다.

**① 병렬도 — OP-A 64x(2.55억 행 조인), `local[N]`**

| master | wall | 피크 RAM | local[1] 대비 |
| --- | ---: | ---: | ---: |
| `local[1]` | 860.8초 | 1.4GB | 1.00x |
| `local[4]` | 335.2초 | 3.4GB | 2.57x |
| `local[16]` | 181.2초 | 8.5GB | 4.75x |
| `local[*]` (22) | 153.9초 | 8.6GB | 5.59x |

코어 22배에 5.6배 — **선형에 한참 못 미친다.** 스레드를 4배 늘릴 때마다 얻는 배수가
2.57 → 1.85 → 1.18로 계속 깎이고, 16 → 22 구간에서는 사실상 포화다.
같은 방향으로 메모리는 1.4GB → 8.6GB로 올라가, **병렬도를 올리는 대가가 메모리**라는 게 드러난다.
단일 머신에서 코어를 더 붙여 교차점(2,000만~5,000만 행)을 앞당기는 건 한계가 있고,
교차점을 실제로 낮추려면 노드를 늘리는 쪽(§4-1)이어야 한다.

**② 셔플 파티션 — OP-B 64x(10.4억 행 집계)**

| `spark.sql.shuffle.partitions` | wall | 피크 RAM |
| --- | ---: | ---: |
| 200 (기본값) | 91.8초 | 2.7GB |
| **32** | **62.4초** | 3.1GB |

**기본값 200을 32로 낮추니 32% 빨라졌다.** 논리 코어 22개짜리 단일 머신에서 파티션 200개는
과분할이라, 태스크 스케줄링·셔플 파일 조각 관리 오버헤드가 실제 계산보다 크게 먹혔다는 뜻이다.
메모리는 0.4GB 늘었다(파티션당 처리량 증가). **로컬·소규모 클러스터에서 이 값은 반드시 손봐야 한다** —
Spark를 도입하는 시점의 체크리스트 1번 항목으로 남긴다.

**③ pivot 값 명시 — OP-C 64x(7.65억 행 pivot)**

| pivot 값 | wall | 피크 RAM |
| --- | ---: | ---: |
| auto (Spark가 distinct 스캔) | **114.4초** | 8.8GB |
| explicit (`["boarding","alighting"]`) | 141.4초 | 8.7GB |

예상과 반대다. 보통 `pivot()`에 값을 명시하면 distinct 값을 찾는 선행 스캔 한 번을 아껴 빨라진다고
알려져 있는데, 여기서는 **명시 쪽이 23.6% 느렸다.** distinct 대상이 2개뿐이라 아낄 스캔이 애초에
거의 없었고(AQE가 이미 처리), 실행 계획이 달라지면서 손해가 난 것으로 보인다.
반복 측정을 1회씩만 했으므로 **이 항목은 단정하지 않는다** — 다만 "pivot 값 명시가 공짜 최적화"라는
통념이 우리 데이터에서는 성립하지 않았다는 사실은 그대로 남긴다.

**세 측정의 공통 결론**: 튜닝으로 Spark를 개선할 여지는 분명히 있지만(②에서 32%),
그 크기가 §2.2의 교차점을 옮길 정도는 아니다. 1,620만 행 구간에서 pandas와의 격차는
세션 기동 7초(§2.5)를 빼고도 남고, 셔플 튜닝으로 메울 수 있는 폭이 아니다.

## 4. 한계 (해석 시 반드시 감안)

1. **단일 머신 측정이다.** `local[*]`는 Spark의 스케줄링·직렬화 오버헤드는 그대로 내면서 다중 노드
   스케일아웃 이점은 하나도 못 낸다. 실제 클러스터에서는 교차점이 더 낮아질 수 있다.
2. **Spark에 8GB 상한을 걸고 pandas에는 안 걸었다.** 대규모 구간에서 pandas에 유리한 설정이다.
   그런데도 16x부터 Spark가 이겼으므로 결론 방향은 견고하다.
3. **증폭 데이터는 합성이다.** 날짜만 민 복제본이라 카디널리티 분포가 실제 대규모 데이터와 다를 수 있다.
4. **OP-B의 요일유형은 근사치다.** 원본 파일에 `day_type` 컬럼이 없어 토·일=weekend로 파생했다
   (실제 배율표는 공휴일을 포함한 정의를 쓴다). 두 엔진에 같은 규칙을 적용했으므로 엔진 비교의
   공정성에는 영향 없지만, 이 표의 집계값을 배율표 값으로 인용하면 안 된다.
5. **Windows 로컬 기준이다.** Spark로 파일을 쓰지 않고 읽기·연산만 했다(winutils/HADOOP_HOME 회피).
   EC2/리눅스에서는 쓰기 경로까지 포함해 다시 재야 한다.
