# 유동인구(서울 생활인구) 피처 검증 (S15P21A104-160 후속)

## 목적

`app/BIKE/pipeline/train.py`(anchor+horizon, `target_net_flow` 예측)의 v3 기준선(22피처)에
유동인구(서울 생활인구, 행정동 단위 합계)를 단독으로 추가했을 때 v3 자체를 이기는지 확인한다.
`bike-floating-population-blocked` 메모(2026-09-16)에서 원본 데이터 기간(2026년 3~8월)이
학습·평가 기간(2024~2025)과 안 겹쳐 보류됐던 걸, 2024-01~2024-12·2025-07~2025-09 전체를
새로 확보해 재개했다.

## 데이터 파이프라인

1. **경계 매핑** — 대여소 위경도 → 행정동코드(point-in-polygon).
   `validation/BYC/floating-population-check/src/build_station_dong_mapping.py`
   - 경계: 서울시 상권분석서비스(영역-행정동) shapefile(EPSG:5181), `ADSTRD_CD` 8자리 코드가
     생활인구 데이터의 `행정동코드`와 동일 체계임을 확인
   - 결과: 대여소 2,583개 전부 매칭(within 2,579 / 최근접 보정 4)
2. **생활인구 집계** — 원본(27GB, 일별 CSV 458개, 격자 단위) → 행정동×일×시간대 합계.
   `validation/BYC/floating-population-check/src/build_dong_hour_population.py`
   - 파일 458개를 스트리밍으로 하나씩 읽어 즉시 groupby-sum(전체를 메모리에 안 올림), 총 257초
   - `생활인구합계`에도 소규모 셀 마스킹(`*`)이 섞여 있어 숫자 변환 실패분은 NaN 처리 후
     합계에서 제외(원칙 8, 채워 넣지 않음)
   - 결과: 4,684,704행, 기간 2024-01-01~2025-09-30, 행정동 428개
3. **피처 조인** — `attach_floating_population()`(anchor 시각 기준, 근사 없음).
   샘플 커버리지(2024-01, 1,078만행 기준): 결측 0.25%뿐, 값 분포 평균 35,914 / 범위
   1,251~223,222(행정동 단위 총 생활인구수)

## 실행 조건 (v3/v4_kbo_lag/v4_weather/v4_distance와 동일)

```
train: 202401~202411 (11개월), valid: 202412, test: 202507~202509
sample_frac: 0.45, n_estimators 1500, learning_rate 0.02, num_leaves 127,
```

## 판정 — 기각

**v4_floating은 v3 대비 사실상 차이가 없다.** 모든 split·모든 지표에서 차이가 소수점
4번째 자리 수준(±0.0001~0.0006)이고, 방향도 지표마다 뒤섞여 있다(valid는 근소 개선,
test:202508·202509는 근소 악화) — `v4_distance`(기각)보다도 더 미미하고, 노이즈와
구분되지 않는다.

**원인 추정**: 이 모델은 이미 `station_code`(역 정체성)와 `historical_profile`(역×시간대
과거 평균)을 피처로 갖고 있어서, 그 역이 "어떤 유형의 동네에 있고 평소 얼마나 붐비는지"가
이미 간접적으로 인코딩돼 있다. 행정동 단위 총 생활인구수(시간대별로만 변하고 역 간 상대적
순위는 거의 고정)는 이 정보에 새로운 신호를 거의 추가하지 못한 것으로 보인다 — `v4_kbo_lag`가
기각됐던 것과 같은 유형의 이유(이미 있는 신호의 재탕).
