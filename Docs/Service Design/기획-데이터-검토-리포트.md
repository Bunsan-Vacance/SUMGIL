## 결론 — 무엇을 선택했고, 왜인가

8일간 **두 가지 방식**으로 14개 후보를 검토해 **혼잡도 도메인**을 선택했고, 후보 4개로 압축했다.

### 두 가지 기획 방식

| | **주제 기준** | **데이터 기준 (혼잡도)** |
| --- | --- | --- |
| 방식 | 다루고 싶은 주제(도메인)를 먼저 정하고, 그에 맞는 데이터를 찾아 서비스를 기획 | 확보 가능한 혼잡도 데이터를 먼저 놓고, 그 데이터로 풀 수 있는 문제를 역으로 설계 |
| 시기 | 8/19 ~ 8/21 | 8/21 ~ 8/26 |
| 후보 | **3건** — 제조, 스포츠, 재난 | **11건** — 유동인구 5 · 도로 2 · 네트워크 1 · 시설 이용 2 · 혼잡도 외 1 |
| 최종 생존 | **0건** | **4건** |
| 상세 | [주제-기준-기획.md](./주제-기준-기획.md) | [데이터-기준-기획.md](./데이터-기준-기획.md) |

8/20 컨설턴트미팅에서 **"데이터를 먼저 선정하는 것에 대한 위험성을 생각해보라"** 는 조언과 **"데이터 양으로 주제를 결정하기는 힘들 것"** 이라는 지적을 동시에 받았다. 어느 한쪽만 택하지 않고 두 방식을 차례로 돌려본 이유다.

**결과적으로 최종 후보 4건이 모두 데이터 기준 트랙에서 나왔다.** 다만 이것이 주제 기준 방식이 무의미했다는 뜻은 아니다 — 자세한 해석은 [3장](#3-두-접근의-비교)에 있다.

### 선택한 후보 (8/26 시점)

| 순위 | 후보 | 혼잡도 갈래 | 선택 이유 |
| --- | --- | --- | --- |
| **1** | **공공시설 입지 최적화** | 유동인구 | **접근성·규모·검증 가능성 3박자를 모두 갖춘 유일한 안.** 생활인구로 규모를 확보하고, 공공자전거 실사용 이력으로 추천 결과를 백테스트할 수 있다. 8/24 리뷰에서 부정 지적 없이 긍정 피드백만 받은 유일한 안이기도 하다 |
| 2 | 응급 | 도로 | 데이터 신뢰도가 조사한 계열 중 최상. 구급측은 기존 서비스와 겹쳐 소거했으나 **사람측(AED 안내·주변인 역할 분배)은 긍정 평가**를 받았다 |
| 3 | 지하철 유동인구 분석 | 유동인구 | 원본은 8.4만 행으로 작지만 통계 무결성을 보존한 증강으로 1억 4,400만 행 확보 가능. 부동산 평가가치·옥외광고 등 **비즈니스 확장 시나리오가 가장 풍부**하다 |
| 4 | 네트워크 혼잡 | 네트워크 | 문제 정의는 좋으나 **원천 데이터 확보가 불가능**해 우선순위가 낮다 |

### 왜 혼잡도였나

**① 팀 합의** — 8/21 1차 투표에서 표가 분산되자 혼잡 vs 제조로 좁혀 2차 토너먼트를 진행했고, **5 : 1** 로 혼잡도가 선택됐다.

**② 데이터가 열려 있었다** — 제조는 설비와 공정을 함께 담은 데이터를 찾지 못했고, 스포츠는 종목이 제한됐으며, 재난은 유입량이 희소했다. 반면 혼잡 계열은 서울시 생활인구·상권·따릉이 데이터가 파일로 즉시 열려 있어 **착수 리스크가 가장 낮았다**.

**③ 하나의 축으로 여러 주제를 담을 수 있었다** — 혼잡도는 유동인구·도로·네트워크·시설 이용으로 갈라지면서도 "혼잡을 계측해 무엇을 할 것인가"라는 공통 질문을 공유했다. 덕분에 11개 후보를 하나의 기준표로 비교할 수 있었다.

**④ 결과가 행동으로 이어진다** — 8/26 기준표 12번(결과가 행동으로 이어지는가)을 충족한다. 히트맵으로 사각지대를 드러내고 Top-N 입지를 추천하는 형태라 분석이 의사결정으로 직결된다.

## 2. 주제 선정 기준의 진화

### 2.1 초기 기준 (8/19)

사실상 두 가지뿐이었다.

- 팀원이 관심 있는 도메인인가
- 공개된 데이터셋이 존재하는가

이 기준으로 스마트팩토리, 이상탐지→생산관리, 설비 예지보전, 재난 알림, 대중교통/도로 혼잡도, 스포츠, 불법 어업, 전력 시스템, 공항 수하물, 반도체 웨이퍼까지 10개 도메인을 넓게 펼쳤다. (롱리스트 전체와 도메인별 수집 데이터는 [주제-기준-기획 1장](./주제-기준-기획.md#1-819-도메인-롱리스트) 참조)

같은 회의에서 명세서(표준 Hadoop Ecosystem = 대용량 배치 처리에 강함)를 근거로 맵리듀스 배치에 적합한 도메인 유형(애드테크 로그 정산, 장바구니 연관 규칙, 카드사 대사, 역색인 구축)과 평가 포인트(Custom Writable/보조 정렬, Combiner, Custom Partitioner와 Data Skew, 노드 수·블록 크기별 벤치마크)를 함께 정리했다. 즉 초기부터 "무엇을 만들까"와 "어떤 분산 기법을 보여줄까"를 분리해서 보고 있었다.

> 9번 항목은 논의 중 제외했다. 대부분의 공공데이터가 과거 축적분을 이미 제공하고 있어 이 기준으로는 후보 간 변별이 되지 않았기 때문이다.

기준표가 만들어진 이후 후보 평가의 언어가 눈에 띄게 바뀌었다. 8/24까지는 "좋다 / 애매하다" 수준의 정성 평가였으나, 8/26 이후에는 **"5, 6번 부합 — 5분 단위 수치로 제어 단계를 즉시 업데이트"**, **"10, 12번 부합 — 실시간 IoT 제어 명령으로 직결"** 처럼 기준 번호를 인용하는 방식으로 바뀌었다.

## 3. 두 접근의 비교

| | **주제 기준** | **데이터 기준 (혼잡도)** |
| --- | --- | --- |
| 후보 수 | 3건 | 11건 |
| 최종 생존 | **0건** | **4건** |
| **데이터 확보 실패** | **1건** (설비·공정 결합 데이터) | **2건** (통신사 기지국, 택시 반출 제한) |
| 주된 소거 사유 | **차별점 부재 · 타겟 미확정 · 데이터 확보 실패** | **서비스·액션 연결 실패 · 차별점 부재** |
| 강점 | **문제의식이 선명하다.** 기획 배경과 페인포인트가 자연스럽게 나오고 발표 스토리를 짜기 쉽다 | **착수 리스크가 낮다.** 데이터가 이미 손에 있으므로 "못 구해서 무산"될 일이 적다 |
| 약점 | **기획을 다 짠 뒤에 데이터에서 막힌다.** 제조가 전형적이다 | **"이걸 왜 하나"를 나중에 만들어야 한다.** 상권이 전형적이다 |

### 관찰된 것

**① 두 방식의 실패 지점이 정확히 반대였다.**
주제 기준은 문제 정의·비즈니스 손실·해결 방식까지 다 짠 뒤에 "그런 데이터가 없다"에 부딪혔다. 데이터 기준은 데이터를 대부분 구할 수 있었지만 **"위험 예측 끝?"(상권), "결과물을 어떤 형식으로 보여주지?"(에너지), "그냥 api 합친거 아닌가"(주차)** 처럼 산출물이 행동으로 이어지지 않는다는 지적에서 걸렸다. 8/20 코치가 양쪽을 동시에 경고한 이유가 여기에 있다.

**② 그래도 순서는 주제 기준이 먼저인 편이 나았다.**
최종 후보 4건이 모두 데이터 기준에서 나왔지만, 주제 기준 트랙이 무의미했던 것은 아니다. **"우리가 무엇에 관심 있는가"를 정리한 것이 그 단계의 성과**였고, 데이터 기준 트랙은 그 관심사를 확보 가능한 데이터에 매핑하는 작업이 됐다. 데이터 기준만 먼저 돌렸다면 8/20에 경고받은 "데이터 우선 선정의 위험"에 그대로 빠졌을 것이다.

**③ 주제 기준의 산출물이 데이터 기준에서 재사용됐다.**
제조에서 설계한 이상탐지 파이프라인(Kafka → Spark Streaming → 이상 점수 → 대시보드)이 이후 전기차 충전소 신뢰도 탐지와 네트워크 이상탐지 안에서 그대로 쓰였다. 도메인은 접혔지만 기술 설계는 살아남았다.

**④ 데이터 기준은 하나의 데이터에 여러 주제를 붙일 수 있었다.**
서울 생활인구 하나로 공공시설 입지, 상권 폐업 예측, 지하철 혼잡 분석, 에너지 최적화, 오버투어리즘까지 5개 주제가 나왔다. 시간대·연령대별 컬럼이 분리돼 있어 "수요"의 정의를 필터 조건만 바꿔 재정의할 수 있다는 데이터의 성질 덕분이다. 주제 기준에서 "이 주제에 맞는 데이터가 없다"로 막혔던 것과 정확히 반대다.

## 6. 검토 결과 정리

### 6.1 8/26 시점 잔존 후보

| 순위 | 후보 | 혼잡도 갈래 | 근거 |

| 2 | **응급** | 도로 | 데이터 신뢰도 최상, 사람측 기능은 긍정 평가 |
| 3 | **지하철 유동인구 분석** (부동산 평가가치, 옥외광고 연결) | 유동인구 | 증강으로 볼륨 확보 + 비즈니스 확장 시나리오 풍부 |
| 4 | **네트워크** | 네트워크 | 문제 정의는 좋으나 데이터 확보 불가 |

함께 정리된 도메인 축: 혼잡도 · 제조 · 스포츠 · 재난 · 데이터 라벨링

### 6.2 이 검토 과정이 남긴 것

**① 두 방식을 병행한 경험**
주제 기준과 데이터 기준을 차례로 돌려보고, 두 방식의 실패 지점이 반대라는 것을 확인했다. 한쪽만 택했다면 데이터에서 막히거나 목적에서 막혔을 것이다.

**② 주제 선정 기준의 정량화**
"관심 있는 도메인 + 데이터 존재"에서 출발해 12개 기준표에 도달했다. 기준표가 생긴 이후 후보 평가 언어가 "좋다/애매하다"에서 "5·6번 부합", "12번 미충족"으로 바뀌었고, 외부 피드백 없이도 자체 기각이 가능해졌다.

**③ 혼잡도라는 공통 축**
유동인구·도로·네트워크·시설 이용으로 갈라지면서도 "혼잡을 계측해 무엇을 할 것인가"라는 질문을 공유했기 때문에, 11개 후보를 하나의 기준표로 줄세울 수 있었다. 축에서 벗어난 부동산 이상거래만 비교 대상에서 빠지며 명시적 소거 기록도 없이 사라졌다.

**④ 분산 처리 명분의 재정의**
"데이터가 크다"에서 **"연산이 무겁다"** 로 축을 옮겼다. 자기 조인·공간 조인의 연산량, 워커 수별 처리 시간 비교 실험, 조합 폭발 계산 — 데이터 크기가 작아도 분산이 유효한 지점을 찾는 쪽으로 설계 방향이 정리됐다.

**⑤ 차별점을 먼저 쓰는 문서 형식**
8/20 이후 모든 기획안이 "무엇이 다른가"를 앞부분에 명시하게 됐고, 8/26에는 그 기준으로 스스로 후보를 접을 수 있게 됐다.

**⑥ 재사용 가능한 데이터 검증 자산**
조사한 데이터·API 47건에 대한 6축 검증과 판정, 그리고 거기서 도출한 원칙 8가지가 남았다. 후보 주제가 바뀌어도 재사용 가능하다 → [데이터-검증-리포트](./데이터-검증-리포트.md)
