## 이 트랙이 무엇이었나

[주제 기준 기획](./주제-기준-기획.md)에서 세 후보가 모두 데이터 확보나 차별점에서 막힌 뒤, 8/21 주제 선정 회의에서 **혼잡도 도메인이 확정**됐다(혼잡 5 : 제조 1).

이후 방식이 뒤집혔다. 주제를 정하고 데이터를 찾는 대신, **서울시가 열어둔 혼잡도 관련 데이터를 먼저 펼쳐놓고 각각에 어떤 주제를 붙일 수 있는지를 설계**했다. 8/21 회의 직후 배정된 과제가 그 성격을 보여준다.

> "오후에 엄청 간단하게라도 브레인스토밍 던져두고 주말에 뭐 해서 올지 봅시다 — **사람 혼잡도로 자료조사 및 기획 배경 비즈니스 가치 알아오기**"

그 결과 혼잡도가 네 갈래로 갈라졌고, 갈래마다 다른 주제가 붙었다.

### 왜 혼잡도였나

8/24 회의에서 후보들을 관통하는 공통 논리를 별도로 정리했다. 어떤 갈래를 택하든 이 논리를 공유한다.

**혼잡도가 중요한 이유**
- 안전
- 응급상황
- 경제
- 건강(생활환경)

**언제 모니터링하는 것이 중요한가**
- **Rush Hours** — 교통 피크 시간대, 공용 네트워크에 많은 사람이 모일 때
- **Large Event** — 콘서트, 스포츠, 연휴 축제
- **재난 상황**

**공통 산출 형태**
- 히트맵으로 시각화
- Top-N 추천

## 1. 유동인구 혼잡도

> **기반 데이터** 서울 생활인구(집계구/250m 격자 × 시간대 × 연령·성별), 상권 유동인구, 지하철 승하차, 실시간 도시데이터
> **후보 5건** — 가장 많은 주제가 붙었고, 최종 1위와 3위가 모두 여기서 나왔다

서울 생활인구는 조사한 데이터 중 **규모 조건을 무조건 만족하는 거의 유일한 계열**(집계구 단위 월 수 GB, 누적 시 수억 행)이었다. 게다가 시간대·연령대별 컬럼이 분리돼 있어 **"수요"의 정의를 필터 조건만 바꿔 재정의할 수 있다**는 점이 여러 주제를 붙일 수 있게 만든 결정적 성질이었다.

### 1.1 공공시설 입지 최적화 플랫폼 ★ 최종 1위

> Wiki `기획안` (상태: 확정/배포) · 회의록 8/24

#### 주제 및 아이디어 개요

> 서울 생활인구·시설 이용 데이터를 분산처리하여 공공시설의 사각지대와 최적 신규 입지를 도출하는 데이터 플랫폼

**유동인구 혼잡도를 "수요"로, 시설 커버리지를 "공급"으로 놓고 그 격차를 찾는다.**

- **정책 배경**: 이태원 참사 이후 정부는 유동인구 데이터를 안전·도시 운영에 활용하는 방향으로 전환했고, 기지국 기반 인파관리지원시스템을 전국 100개 중점관리지역에서 운영 중이다. 유동인구 빅데이터의 공공 활용이 국가적 과제로 부상했다.
- **현장 문제**: 시설 신설·증설이 민원과 담당자 경험 위주로 결정되어 실제 유동인구 수요와 공급이 불일치한다. 따릉이의 "빈 스테이션 / 포화 스테이션" 문제가 고질적인 것이 그 예다.
- **핵심 질문**: ①수요는 많은데 공급이 없는 사각지대는 어디인가 ②시간대별 수요-공급 불균형이 반복되는 지점의 재배치 우선순위는 ③신규 1곳을 추가한다면 어디에 놓아야 커버리지가 최대가 되는가
- **타겟**: 1차 서울시설공단·지자체 담당자(B2G) / 2차 시민

#### 찾아본 데이터

서울 생활인구, 공공자전거 대여이력·대여소 정보, 집계구 경계(shp), 지하철 승하차, 실시간 도시데이터 — 6종. **공공자전거는 실사용 이력이 공개된 시설이라 추천 결과를 실제 이용률로 백테스트할 수 있는 유일한 조합**이었고, 이것이 1차 대상으로 삼은 근거다.

#### 데이터 활용 방안

```
[공공데이터 API/파일]
        │  수집 (Python, 스케줄링)
[Object Storage / HDFS]  ← 원본(Raw) 적재
        │
[Spark 분산 배치]  ─ 정제·조인·집계 (생활인구 × 이용이력 × 시설좌표)
        │            └ 공간 조인(집계구·버퍼), 입지 스코어링
[서비스 DB (PostgreSQL/PostGIS)]
        │
[백엔드 API (Spring Boot)] → [프론트 대시보드 (React + 지도 시각화)]

* 전체 워크플로우 오케스트레이션: Airflow
```

**주요 기능**
- **사각지대 히트맵** — 집계구 단위 유동인구 밀도 위에 기존 시설 커버리지(반경 300m 버퍼)를 오버레이해 수요 대비 공급 부족 지역을 색상으로 시각화
- **신규 입지 추천 Top-N** — 입지 스코어 = f(유동인구 밀도, 기존 시설 거리, 지하철역 접근성, 인접 시설 이용률) + 근거 지표 카드
- **시설 진단 리포트** — 시간대·요일별 이용 패턴 분석, 만성 불균형 지점 자동 분류 및 재배치 우선순위
- **배치 리포트 자동화** — Airflow로 신규 데이터 반영 배치 → 대시보드 자동 갱신

**확장 구조 — 이 안의 핵심 아이디어**

"수요 레이어 × 공급 레이어" 프레임워크로, 파이프라인의 약 90%(생활인구 수요 산출, H3 격자, 커버리지 계산, 스코어링, 히트맵)를 재사용하고 시설별로 3가지만 교체한다.

| 교체 요소 | 공공자전거(1차 검증) | 무더위 쉼터 | 공공와이파이 | 전기차 충전소 |
| --- | --- | --- | --- | --- |
| 공급 좌표 데이터 | 대여소 정보 | 쉼터 위치 | AP 위치 | 충전소 위치 |
| 커버 반경 | 300m | 도보 5분(약 400m) | 수십 m | 500m~ |
| 수요 정의 | 전 연령 유동인구 | 여름 낮 시간대 × 고령층 | 청년층 유동인구 | 차량 보유 지역 가중 |

생활인구 데이터가 시간대·연령대별 컬럼을 제공하므로 수요 정의 변경은 필터 조건 수정만으로 가능하다. 시설별 설정을 config로 분리해 코드 수정 없이 전환하고, 발표에서는 1차 시설 분석 시연 후 config만 바꿔 무더위 쉼터 사각지대를 즉석 산출해 **"분석기"가 아닌 "플랫폼"** 임을 증명하는 시나리오를 설계했다.

> 이 확장 구조가 **네트워크 혼잡도(3장)의 공공와이파이와 시설 이용 혼잡도(4장)의 전기차 충전소를 흡수한 통로**가 됐다.

**차별화 포인트** — ①수억 행을 실제 분산 클러스터에서 처리하고 단일 노드 대비 처리 시간 비교 실험을 발표에 포함 ②단순 집계가 아닌 커버리지 버퍼·공간 조인 등 GIS 분석을 분산 환경에서 수행 ③실제 이용률로 백테스트 가능 ④타 시설로 확장 가능한 플랫폼 구조

**리스크 대응** — 공간 조인 성능 이슈는 H3/GeoHash 그리드 인덱싱으로, 클러스터 비용·환경 제약은 로컬 Docker 멀티 노드로 시작하고 성능 실험만 클라우드를 활용.

### 1.2 상권 폐업 조기경보 시스템 (상권온도계)

> Wiki `기획안(유동인구) ← 상권 ?` (상태: 확정/배포) · 회의록 8/24

#### 주제 및 아이디어 개요

> 사람이 많은 상권을 찾는 것이 아니라, 수요보다 점포와 임대료가 빠르게 증가해 지속 가능성이 떨어지는 상권을 찾아낸다.

**같은 유동인구 데이터에 "혼잡이 곧 기회는 아니다"라는 역발상을 붙인 안이다.**

- **배경 근거**: 2024년 기준 국내 활동기업 약 764만 개, 2023년 소멸기업 약 79만 개. 신생기업 1년 생존율 64.4%, 5년 생존율 36.4%. 도·소매업 1년 생존율은 55.2%. (국가데이터처 기업생멸행정통계)
- **문제의 본질**: "상권의 실질 수요 증가 속도보다 점포 공급과 영업비용이 빠르게 증가하는 현상을 너무 늦게 발견하는 것"
- **분석 단위**: 분기 × 상권 × 업종
- **예측 대상**: 다음 분기 폐업률(회귀) / 동일 업종 내 상위 20% 고위험 여부(분류)
- **위험 유형 4종**: 수요 위축형 / 경쟁 과열형 / 임대료 압박형 / 복합 위험형

#### 찾아본 데이터

서울 열린데이터광장 상권 계열 8종(생활인구·상권 유동인구·추정매출·점포 개폐업·상주직장인구·집객시설·실시간 도시데이터·상권변화지표) + 부동산 보조 4종(한국부동산원 임대동향조사·매장용빌딩 임대료·상업용 매매가·공시지가). 임대료는 공간 기준 불일치와 커버리지 문제가 있어 **핵심 데이터와 동일하게 취급하지 않는다**는 방침을 세웠다.

#### 데이터 활용 방안

```
서울시 상권·유동인구 데이터 / 한국부동산원 임대료·공실률 / 서울 실시간 도시데이터
                 ↓  데이터 수집 서버
               Kafka
                 ↓
        HDFS Bronze (원천)
                 ↓  Spark 정제·시간·공간 통합
        HDFS Silver (정제)
                 ↓  Spark 파생변수 생성·통계 집계·학습
        HDFS Gold (분석 결과)
                 ↓  백엔드 API
     상권 위험지도 · 분석 대시보드
```

**핵심 파생지표**

```
수요-공급 격차   = 공급 증가율(점포 수·신규 개업) - 수요 증가율(유동인구·추정매출·결제 건수)
임대료 압박 격차 = 임대가격지수 증가율 - 점포당 매출 증가율
```

- **Spark ML**: 트리 기반 모델(Random Forest, GBT) 우선 — 정형 데이터에 적합하고 변수 중요도 설명이 쉽다. 딥러닝은 명확한 성능 향상이 확인될 때만 검토.
- **Kafka의 역할 규정**: 폐업률은 분기 단위로 계산되므로 전체 예측을 5분마다 다시 할 필요는 없다. Kafka는 실시간 도시데이터 수집, 수집-분석 시스템 분리, 과거 데이터 시간 순 재생, 현재 상권 활력지표 갱신에만 사용한다. → **기술을 쓰기 위해 억지로 붙이지 않고 역할을 한정한 사례**
- **평가 지표**: MAE/RMSE(회귀), Precision·Recall·F1·PR-AUC(분류)에 더해 서비스 관점 지표 — "위험도 상위 10% 상권의 실제 폐업률이 서울 전체 평균보다 몇 배 높았는가", "임대료 데이터 추가 전후 성능 차이"

#### 검토 결과 및 미채택 사유

| 시점 | 피드백 |
| --- | --- |
| 8/24 | "위험 예측 끝? 은 우리 프로젝트 위험" |

핵심 지적은 **결과가 위험 점수 하나로 끝나면 사용자가 취할 행동이 없다**는 것이었다(12기준 12번 미충족). 대응으로 경쟁 업체 시각화, 주변 이벤트/행사에 따른 마케팅 인사이트 제안 등의 확장안이 나왔으나 채택되지 않았고, 8/26 회의록에서 해당 항목에 취소선이 그어졌다.

### 1.3 지하철 유동인구 분석 및 온디맨드 파이프라인 ★ 최종 3위

#### 주제 및 아이디어 개요

#### 데이터 활용 방안

**① 분 단위에서만 추출 가능한 고부가가치 피처**
- **과밀 급증 속도(Surge Slope)** — 1시간 단위로는 보이지 않는 특정 10~15분간의 승하차 폭발 기울기(미분값)를 계산해 병목·과밀 위험도를 정량화
- **역사 내 실시간 체류 인원 추정** — 분 단위 (승차 - 하차) 차이값을 누적 적분해 특정 시점 승강장/개찰구 내 잔류 인원 파악

**② AI 기반 초단기 예측 및 이상 감지**
- 직전 30분간 분 단위 유입 속도를 학습해 15~30분 뒤 혼잡도 임계치 돌파 여부 조기 예측
- 통상 평일/주말 패턴을 벗어난 비정상 유입 징후를 감지해 위험 경보 레벨 산출

**③ 비즈니스 확장 — 유동인구 × 부동산 임대료**
- 피크 시간대 순유입량·체류 지수와 부동산 평균 임대료/매매가를 결합해 **역세권 상권 가치**의 저평가/고평가 판별
- 유동인구 대비 임대료가 저평가된 출점 입지 추천 및 공실 위험(거품 상권) 분석

**④ 온디맨드 인터랙티브 아키텍처**
1회성 배치에 그치지 않고, 웹에서 사용자가 특정 역사·세부 시간대·조건을 선택해 조회를 요청하면 백엔드 분산 엔진이 HDFS 상의 대용량 로그에서 해당 구간을 즉시 추출·연산해 결과를 반환한다.

**추가로 검토한 수익화 시나리오** — DOOH 다이내믹 프라이싱(분 단위 광고 노출 지수로 실시간 단가 할증/할인), 라스트마일 모빌리티 재배치(10분 단위 급증 하차량을 선행 지표로 활용), F&B 초단기 수요 예측(피크 15분 전 준비 스케줄링, 앱 푸시 타임세일), 배달 라이더 거점 배치(주거지 역 퇴근 하차 급증을 주문 폭발의 15~30분 선행 시그널로 활용)

### 2.2 택시 수요 예측 및 기사 재배치 추천

> 회의록 8/21 내 상세 기획 (도로 혼잡도 섹션)

#### 주제 및 아이디어 개요

**도로 혼잡도에 "이동 수요 예측"을 붙인 안이다.** 과거 택시 승하차 패턴과 실시간 교통·날씨·행사·택시 공급 데이터를 분석해 지역별 15~30분 후 승객 수요를 예측한다. 단순 Hotspot 제공이 아니라 현재 기사 위치와 지역별 택시 공급까지 고려해 **승객 확보 가능성이 높은 지역을 기사에게 실시간 추천**한다. 동일 지역으로 택시가 몰리지 않도록 실시간 공급량을 반영해 추천을 동적으로 갱신한다.

#### 찾아본 데이터

**17종 결합을 설계했다 — 조사한 후보 중 소스 다양성이 가장 높다.** 택시 운행 1종, 인구 4종(실시간 도시데이터·생활인구·체류인구·생활이동), 대중교통 3종, 도로 2종, 환경·이벤트 4종(날씨·문화행사·스포츠 경기·달력), 상권 2종, 기타 이동수단 2종(따릉이·김포공항 운항). 다만 정답 데이터인 서울 빅데이터캠퍼스 택시 데이터가 현장 이용·반출 제한이라 확보하지 못했다.

#### 데이터 활용 방안

```
Taxi Historical → HDFS/Spark Batch → 수요 모델
Taxi/교통/날씨 Event → Kafka → Spark Structured Streaming
   → GeoHash×Window 집계 → 지역별 수요·공급 예측 → Redis → 기사 지도
```

ML은 XGBoost/LightGBM 기반 지역별 단기 수요 예측 + 수요/공급/이동시간 기반 추천 Score. 최종 서비스는 기사에게 **"주변에서 어디로 이동해야 승객을 가장 빨리 확보할 수 있는지"** TOP 3 지역과 예상 이동시간·승객 수요·택시 공급 수준을 제공한다.

**장점으로 본 것** — 대용량 Batch + 실시간 Streaming + 시공간 데이터 + Data Skew + 실시간 추천을 모두 경험할 수 있고 Kafka/Spark/HDFS/Redis 각각의 역할이 명확하다. 단순 분석이 실제 택시 수요-공급 최적화 서비스로 연결된다.

#### 검토 결과 및 미채택 사유

8/21 논의에서 응급 쪽으로 초점이 옮겨가며 독립 후보로 이어지지 않았다. **정답 데이터의 반출 제한이 결정적이었다** — 17종 중 16종을 확보해도 학습 정답이 되는 택시 운행 데이터가 없으면 모델을 만들 수 없다.

### 3.1 Wi-Fi 혼잡 해소 서비스

> Wiki `기획하기(와이파이)` (상태: 작성 중) · 회의록 8/24

문서 첫 줄이 **"사람 혼잡도(HUMAN CONGESTION)"** 로 시작한다. 사람이 몰리는 현상 자체는 유동인구 갈래와 같고, 그 결과로 나타나는 **네트워크 품질 저하**에 초점을 맞춘 안이다.

#### 주제 및 아이디어 개요

**빅데이터 분산 기반 인구 밀집 네트워크 혼잡 해소 서비스**

- **문제의 본질**: 5G/6G 시대에도 "특정 시간, 특정 장소에 사람이 몰리는 순간"의 네트워크 품질은 해결되지 않았다. 통신 인프라의 절대적 용량 부족이 아니라 **수요가 시공간적으로 극단적으로 쏠리는 현상(스파이크성 밀집)** 때문이다.
- **발생 상황**: 대규모 공공 행사(스타디움·페스티벌), 도심 교통 허브(지하철·공항 러시아워), 재난/비상 상황(대피 인파의 응급 연락 폭증), 고밀도 실내 공간(사무실 점심시간·전시장·병원)
- **기술적 원인**: ①무선 채널 경쟁(동일 주파수 대역 동시 점유 → 패킷 충돌·손실 급증) ②백홀 용량 한계 ③인체에 의한 물리적 신호 감쇠
- **사용자 체감**: 일반 상황에서는 로딩 지연·SNS 업로드 실패·결제 지연이지만, 비상 상황에서는 가족 안전 확인 실패·긴급 신고 지연으로 **단순 불편이 아닌 안전 이슈**가 된다
- **핵심 아이디어**: "혼잡을 없앨 수는 없지만, 혼잡도를 실시간으로 계측하고 트래픽을 여러 경로로 나누어 처리하면 체감 품질을 개선할 수 있다."

#### 찾아본 데이터

기지국·AP 원천(통신사), 자체 앱 크라우드소싱, 플로우 메타데이터, 공개 침입탐지 데이터셋 3종(CICIDS2017·NSL-KDD·UNSW-NB15). **핵심인 기지국 원본은 "계약상 정부기관도 받지 못할 만큼 폐쇄적"이라 확보 불가로 판정**했고, 대안으로 설계한 크라우드소싱은 표본·콜드스타트 문제로 프로젝트 기간 내 유효 데이터를 모을 수 없었다.

#### 데이터 활용 방안

3단계 구조로 설계했다.

1. **Sensing Layer** — AP 접속 기기 수·RSSI·패킷 손실률 실시간 스트리밍 수집 + 앱 기반 익명 크라우드소싱
2. **Big Data / AI Layer** — Kafka, Spark Streaming/Flink 스트림 처리 → 과거 이벤트 데이터(공연 시작 시각, 경기 종료 시각)와 실시간 지표를 결합한 LSTM 시계열 예측으로 혼잡 피크 사전 예측 → Congestion Heatmap 생성
3. **Action Layer** — Wi-Fi 오프로딩 유도, 핸드오버 최적화, MEC(현장 근처 엣지 처리), 5G Network Slicing(긴급 통신 우선순위 분리), 이동형 기지국(COW) 사전 배치 위치·시점 추천

**이상탐지 확장** — 같은 파이프라인 위에 추가 인프라 없이 얹을 수 있는 기능으로 설계했다. AP 혼잡도 급변(베이스라인 대비 이탈), Evil Twin(동일 SSID에 미관측 BSSID가 다수 사용자에게 관측되는 패턴), 비정상 연결 끊김(짧은 시간 내 동시다발 해제), 개인 연결 상태 이상. 알고리즘은 Isolation Forest / Autoencoder / One-Class SVM.

#### 검토 결과 및 미채택 사유

| 시점 | 피드백 원문 |
| --- | --- |
| 8/24 | "그냥 데이터 쓰지 않을까" |
| 8/24 | "문제 정의는 좋은데, 명확한 솔루션 연결이 더 필요" |

첫 번째 피드백이 이 안의 전제를 무너뜨렸다 — 사용자가 혼잡한 Wi-Fi 대신 모바일 데이터를 쓰면 그만이므로, 문제 자체의 절실함이 약하다는 지적이다. 여기에 원천 데이터 확보 불가가 겹쳐 진행하지 않기로 했다. **8/26 후보 리스트 4번으로 잔존**했으나 우선순위는 낮았고, 공공와이파이 입지 분석이라는 형태로 [공공시설 입지 최적화(1.1)](#11-공공시설-입지-최적화-플랫폼--최종-1위)의 확장 대상에 흡수됐다.

### 4.1 전기차 충전소 혼잡도 & 신뢰성 예측 서비스

> Wiki `기획하기(전기차충전소)` (상태: 작성 중)

#### 주제 및 아이디어 개요

- **배경**: 2026년 기준 국내 전기차 100만 대, 누적 충전기 40만 기를 돌파했지만 급속 충전기는 전기차 16대당 1기꼴로 보급 속도가 수요를 따라가지 못한다. 충전은 급속 기준 80%까지 최소 30분~1시간이 소요되어, **한 번의 혼잡이 도로 정체보다 훨씬 긴 대기로 이어진다**(주유 5분 vs 충전 30분+).
- **차별화 전제**: "충전소 찾기 + 예약"은 이미 채비, EV Infra, EVZone 등이 제공하는 레드오션이다. 기존 서비스가 잘하는 위치 안내를 반복하지 않고, **여러 운영사 데이터를 통합·검증해 "진짜 믿을 수 있는 실시간성"을 만드는 것**에 집중한다.

**핵심 페인포인트**
1. **표시된 정보와 실제 현장이 다름** — 공식 앱에서 "사용 가능"으로 표시돼도 실제로는 고장 중이거나 이미 다른 차량이 충전 중인 경우가 잦다.
2. **충전 구역 점유 갈등** — 충전하지 않고 제한시간 내 주차만 하는 차량이 법적 위반이 아니라는 유권해석 이후, 실질적으로 충전기가 점유돼도 이용자가 사전에 알 방법이 없다.
3. **대기시간 예측 부재** — 기존 앱은 "지금 비어있는지"만 알려줄 뿐 "내가 도착하는 시점에 얼마나 기다릴지"는 알려주지 못한다.
4. **운영사 파편화** — 앱마다 커버하는 충전소가 달라 완전한 그림을 보기 어렵다.

#### 찾아본 데이터

한국환경공단 충전소 정보 API, 전국전기차충전소표준데이터, 환경부 충전건별 충전량 + 보조로 기상·고속도로 통행량. 민간 운영사 API(채비·SK일렉링크·워터)는 제휴가 필요해 MVP에서 제외했다. **운영사마다 상태값 갱신 주기가 달라 발생하는 신뢰도 문제 자체가 이 안의 주제**다.

#### 데이터 활용 방안

| 축 | 내용 |
| --- | --- |
| ① 통합 상태 표시 | 환경부·한전 등 복수 운영사 API의 충전기 상태정보를 하나의 지도에 통합 |
| ② 데이터 신뢰도 이상탐지 | API상 "사용가능"인데 상태갱신일시가 임계치 이상 오래됐거나, 동일 충전기가 짧은 시간 내 상태값을 비정상적으로 자주 반복하면 이상치로 플래깅 → **"진짜 사용가능" 스코어**로 보정 |
| ③ 대기시간 예측 | 과거 충전 세션(시작~종료 시각) 데이터를 학습해 "지금 출발하면 도착 시점에 대기 몇 분"을 예측. MVP는 요일·시간대별 평균 통계 모델 → 데이터 축적 후 ML 고도화 |
| ④ 크라우드소싱 보정 | 도착 후 "표시와 다르다"를 1탭 리포트 → 신뢰도 스코어 실시간 반영. 리포트 불일치 사례를 라벨로 활용해 지도학습으로 전환 |
| ⑤ 대안 제안 | 목적지 인근에서 신뢰도·대기시간이 더 나은 충전소를 제안 (강제 아닌 제안형 UX) |

**분산 처리가 필요한 지점** — 전국 수만 개 충전기의 상태값을 주기적으로 폴링·스트리밍 수집해 실시간 신뢰도를 재계산하고, 다수 운영사 API를 병렬로 수집·정합성 대조하는 구조. 배치가 아닌 지속적 스트림 처리다.

**설계 원칙 5가지** — ①위치 안내가 아닌 신뢰도 검증이 핵심 가치 ②개인 식별 없는 집계 데이터만 사용 ③검증된 정보만 "신뢰" 표시, 확신 없는 정보는 과신하지 않음 ④제안이지 강제가 아님 ⑤공공 데이터 우선, 민간 제휴는 검증 후 확장

#### 검토 결과

독립 후보로는 채택되지 않았으나, [공공시설 입지 최적화(1.1)](#11-공공시설-입지-최적화-플랫폼--최종-1위)의 **확장 대상 시설 중 하나**로 흡수됐다. 신뢰도 검증을 서비스의 핵심 가치로 삼은 관점은 이후에도 재사용 가치가 있다.

### 4.2 경량 검토안 — 가변 주차 요금 및 주차장 수요 예측

## 5. 혼잡도 외 — 부동산 실거래 이상거래

> 회의록 8/26

데이터를 먼저 놓은 트랙이지만 **혼잡도 축에서 벗어난 유일한 후보**다. 국토부 실거래가라는 대용량 raw 데이터가 출발점이었다.

### 주제 및 아이디어 개요

집값 띄우기(신고 후 해제), 증여성 저가 거래, 깡통전세 등 부동산 이상 거래가 사회적 문제로 반복되고 있다. 국토부 실거래가 공개 데이터는 거래 건별 원본(raw)으로 제공되지만, 전국 20년치 수천만 건을 수집·정제·분석하려면 분산 처리 파이프라인이 필요하다. 공공 raw 데이터를 자체 분산 파이프라인으로 처리해 이상 의심 거래를 스코어링하고 지역별 위험 지도를 제공한다.

**탐지 모듈 4종**
1. **가격 이상치** — 단지×평형×기간별 시세 분포 대비 비정상 고가/저가 거래
2. **신고 후 해제(집값 띄우기)** — 신고가 경신 후 해제된 거래 → 직후 유사 가격 거래 성사 여부 연결 분석
3. **단기 반복 거래** — 동일 물건의 단기간 반복 매매 및 계단식 가격 상승 패턴
4. **전세가율 이상(깡통전세)** — 매매×전월세 조인으로 전세가율 급등 물건·지역 탐지, 신축 빌라 가중

### 찾아본 데이터

국토부 실거래가 3종(아파트 매매·아파트 전월세·연립다세대 오피스텔) + 건축물대장 + 지하철역·학교 위치. 합계 **약 5,000만 건으로 조사한 데이터 중 원본 볼륨이 가장 컸다.**

### 데이터 활용 방안

```
[수집기 (Python, Airflow 스케줄링)]
        ↓  API 폴링 (증분·재시도·중복 방지)
[데이터 레이크 (MinIO + Parquet, 원본/정제 계층 분리)]
        ↓
[Spark 클러스터 (마스터 1 + 워커 2~3, Docker Compose)]
        ├─ 정제·중복 제거·정정/해제 처리
        ├─ 시세 기준선 집계 (대규모 그룹 연산)
        ├─ 근사 매칭 자기 조인 / 공간 조인 (연산 집약)
        └─ 탐지 모듈 4종 실행 → 이상 스코어
        ↓
[서빙 DB (PostgreSQL)] → [대시보드 (Streamlit/Grafana, 지도 시각화)]
```

산출물은 거래별 이상 스코어 테이블 + 지역(시군구/동) 단위 위험 지수. 6인 역할 분담(수집 2 / 탐지 모듈 2 / 인프라 1 / 시각화·서빙 1)과 5주 일정까지 구체화됐다.

분산 처리의 명분을 원본 크기가 아니라 **자기 조인·공간 조인의 연산량**에 둔 것이 이 안의 특징이다. 워커 수별(1/2/3) 처리 시간 비교 실험을 발표에 포함해 분산 유효성을 정량 증명하는 계획을 세웠다.

### 검토 결과 및 미채택 사유

기술적 조건(볼륨, 연산 집약도, 리스크 대응)은 잘 갖춰졌으나 **8/26 후보 압축 과정에서 리스트에 오르지 못했다.** 회의록에 명시적 소거 사유가 남아 있지 않다. 정황상 **혼잡도라는 공통 축에서 벗어난 유일한 안이라 트랙 연속성이 끊긴 것**으로 보인다.

### 6.2 관찰된 것

**① 하나의 데이터에 여러 주제를 붙일 수 있었다.**
서울 생활인구 하나로 공공시설 입지, 상권 폐업 예측, 지하철 혼잡 분석, 에너지 최적화, 오버투어리즘까지 5개 주제가 나왔다. 시간대·연령대별 컬럼이 분리돼 있어 **"수요"의 정의를 필터 조건만 바꿔 재정의할 수 있다**는 데이터의 성질이 이를 가능하게 했다. 주제 기준 트랙에서 "이 주제에 맞는 데이터가 없다"로 막혔던 것과 정확히 반대 상황이다.

**② 이 트랙의 실패는 데이터가 아니라 목적에서 났다.**
후보 11건 중 데이터 확보에 실패한 것은 네트워크(기지국)와 택시(반출 제한) 둘뿐이고, 나머지는 모두 데이터를 구할 수 있었다. 대신 **"위험 예측 끝?"(상권), "결과물을 어떤 형식으로 보여주지?"(에너지), "그냥 api 합친거 아닌가"(주차)** 처럼 산출물이 사용자의 행동으로 이어지지 않는다는 지적에서 걸렸다. 데이터를 먼저 놓는 방식의 구조적 약점이다.

**③ 흡수가 일어났다.**
공공시설 입지의 "수요 레이어 × 공급 레이어" 확장 구조가 다른 갈래의 후보들을 빨아들였다. 네트워크 혼잡도의 공공와이파이, 시설 이용 혼잡도의 전기차 충전소, 유동인구 갈래의 에너지 효율화가 모두 config 교체 대상 시설로 정리됐다. 개별 후보로는 약했던 안들이 하나의 플랫폼 안에서 확장 시나리오가 된 셈이다.

**④ 혼잡도라는 축이 후보 간 비교를 가능하게 했다.**
모든 후보가 "혼잡을 계측해 무엇을 할 것인가"라는 같은 질문에 답하는 형태였기 때문에, 8/26 12기준표로 한 번에 줄세우기가 가능했다. 축에서 벗어난 부동산 이상거래만 비교 대상에서 빠지며 명시적 소거 기록도 없이 리스트에서 사라졌다.
