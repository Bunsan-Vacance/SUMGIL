# 데이터 검증 리포트

**대상 기간** 2026-08-19 ~ 2026-08-26
**작성 목적** 주제 검토 과정에서 조사한 데이터·API를 6개 축으로 검증하고, 프로젝트에 실제로 투입 가능한지를 판정한 기록이다.
**관련 문서** [기획-데이터-검토-리포트.md](./기획-데이터-검토-리포트.md) — 아이디어별 기획 맥락과 의사결정 과정

## 결론 — 무엇을 선택했고, 왜인가

조사 항목 **47건**을 6개 축으로 검증했다. 그 결과 **✅ 26건(55%) · ⚠️ 16건(34%) · ❌ 5건(11%)** 으로 판정했고, 8/26 시점 주력 후보(공공시설 입지 최적화)의 기반으로 아래 조합을 선택했다.

### 선택한 데이터

| 역할 | 데이터 | 선택 이유 |
| --- | --- | --- |
| **수요 레이어** | 서울 생활인구 | **6축을 모두 통과한 유일한 대용량 계열.** 집계구 단위 월 수 GB로 규모 조건을 만족하고, 시간대·연령대별 컬럼이 분리돼 있어 수요 정의 변경이 필터 조건 수정만으로 가능하다 |
| **공급·검증 레이어** | 공공자전거 대여이력 + 대여소 정보 | **실사용 전수 이력이 공개된 시설.** 추천 결과를 실제 이용률로 백테스트할 수 있는 유일한 조합이다 |
| **공간 결합** | 집계구 경계(shp) | 집계구·행정동·250m 격자로 갈린 단위를 통일하는 데 필수 |
| **보조 피처** | 지하철 역별 승하차 | 접근성 변수. 규모는 작으나 조인 대상으로만 사용 |
| **시연·활력 지표** | 서울 실시간 도시데이터 | 호출 제한과 지역 제한(120~121개 장소)이 있어 메인 분석에는 쓰지 않고 시연·보조 지표로 역할을 한정 |

### 선택 근거 세 가지

**① 규모 조건을 만족하는 계열이 사실상 하나였다.** 조사한 47건 중 원본 그대로 분산 처리 명분이 서는 것은 생활인구 계열과 국토부 실거래가 계열뿐이었다. 나머지는 증강(지하철 8.4만 행), 폴링 축적(응급 조회형 API), 다년치 누적이 선행돼야 했다.

**② 검증 가능성이 후보를 갈랐다.** 공공데이터 상당수가 추정·표본 데이터여서 모델 성능을 확인할 정답이 없었다. 공공자전거는 실사용 이력이 공개돼 백테스트가 가능한 예외였고, 이것이 다른 시설(무더위 쉼터·공공와이파이·전기차 충전소)로 확장하기 전 1차 대상으로 삼은 이유다.

**③ 확보 불가 데이터가 후보를 무너뜨렸다.** ❌ 5건 중 4건이 민간 보유이거나 표본 확보 실패였고, 이 5건이 각각 네트워크 혼잡·택시 수요예측·응급 경로 추천·전기차 충전소 후보의 핵심 데이터였다. **데이터가 존재하는지와 우리가 5주 안에 받을 수 있는지는 별개 문제**라는 것이 검증 과정의 가장 큰 소득이다.

### 선택하지 않은 것

| 데이터 | 불가 사유 |
| --- | --- |
| 통신사 기지국 원본 데이터 | "계약상 정부기관도 받지 못할 만큼 폐쇄적" |
| tmap 등 민간 도로 혼잡 데이터 | 확보 경로 없음 |
| 민간 충전 운영사 API (채비·SK일렉링크·워터) | 개별 제휴 필요 |
| AP 크라우드소싱 리포트 | 표본·콜드스타트로 기간 내 유효 표본 확보 불가 |
| 서울 빅데이터캠퍼스 택시 데이터 | 현장 이용·반출 제한 |

## 1. 검증 프레임워크

### 1.1 검증 6축

| 축 | 확인 내용 | 왜 보는가 |
| --- | --- | --- |
| **① 사이즈** | 행/건 수, 파일 용량, 누적 가능 기간 | 분산 처리 명분(Spark/Hadoop)이 서는가 |
| **② 형태** | 원시(raw) vs 집계 가공본 / 정형·비정형 / 공간·시계열 / 스키마 안정성 | 그대로 쓸 수 있는가, 역산·증강이 필요한가 |
| **③ 신뢰도** | 전수 / 표본 / 추정 / 합성 · 구축 주체 · 라벨 유무 | 결과를 어디까지 단정할 수 있는가 |
| **④ 주기·최신성** | 실시간 / 5·10·15분 / 시간 / 일 / 월 / 분기 / 정적 스냅샷 | 스트리밍 명분이 서는가, 최신성이 유효한가 |
| **⑤ 접근성** | 즉시 다운로드 / 활용 신청 / 승인 / 호출 한도 / 제휴 필요 / 확보 불가 | **5주 안에 실제로 손에 넣을 수 있는가** |
| **⑥ 활용 가능 여부** | 위 5축 종합 판정 | 최종 채택 여부 |

⑤번 축은 검토 초반에는 없었다. 8/20 컨설턴트미팅 이후 "데이터가 존재한다"와 "우리가 받을 수 있다"가 전혀 다른 문제라는 것이 드러나면서 별도 축으로 분리했고, 이후 후보 스크리닝의 1차 관문이 됐다.

### 1.2 판정 기준

| 판정 | 정의 |
| --- | --- |
| ✅ **가능** | 즉시 또는 활용 신청만으로 확보 가능하고, 목적한 분석에 그대로 투입할 수 있다 |
| ⚠️ **조건부** | 확보는 가능하나 규모·최신성·커버리지·호출 한도 등 제약이 있어 **보완 설계가 선행돼야** 한다 |
| ❌ **불가** | 계약·제휴·반출 제한·표본 확보 실패로 프로젝트 기간 내 확보가 불가능하다 |

### 1.3 "사이즈"를 보는 관점

①번 축은 검토 과정에서 의미가 한 차례 바뀌었다. 처음에는 "행 수가 많은가"였지만, 8/20 컨설턴트 조언 이후 **"연산량이 무거운가"** 로 이동했다.

> "데이터 규모로 따지자면 현업에서의 분산은 되지 않는다. 다만 **분산 설계를 해보는 것 자체로 가치**가 있기 때문에 도메인이나 도메인 규모가 중요하지는 않다."
> "많지 않은 데이터지만 분산 시스템으로 처리할 것이다. **분산 구조를 구현하고 기술을 써보는 게 핵심.**"

따라서 본 문서의 사이즈 판정은 원본 행 수만이 아니라 **자기 조인·공간 조인·조합 폭발 등 연산 집약도**를 함께 고려한다. 원본이 작아도 조인 연산이 무거우면 ⚠️가 아니라 ✅에 가깝게 봤다.

## 3. 데이터 계열별 상세 검증

### 3.1 유동인구 · 생활인구 계열

**여러 후보에서 공통으로 쓰인 기반 데이터다.** 상권 폐업 예측, 공공시설 입지 최적화, 택시 수요 예측, 스마트시티 에너지 최적화가 모두 이 계열 위에 서 있다.

| 축 | 검증 결과 |
| --- | --- |
| 사이즈 | 서울 생활인구는 집계구 단위 기준 월 수 GB, 누적 시 수억 행. **규모 조건을 무조건 만족하는 거의 유일한 계열** |
| 형태 | 집계구/행정동 × 시간대 × 연령/성별 컬럼 구조. 시간대·연령대별 컬럼이 분리돼 있어 **수요 정의 변경이 필터 조건 수정만으로 가능** |
| 신뢰도 | 통신 데이터 기반 **추정**. 특정 시간·공간에 실제로 머무는 인구를 추정하며 약 250m 격자 단위로 제공 |
| 주기 | 생활인구는 파일 배치(D+4 공개), 실시간 도시데이터는 5분 주기 |
| 접근성 | 파일은 로그인 후 즉시 다운로드. 실시간 API는 활용 신청 후 자동 승인(즉시~1일)이나 **호출 제한 존재** |
| 판정 | ✅ (실시간 도시데이터만 ⚠️) |

**확인된 제약과 대응**

- **추정 데이터의 절대값 신뢰 문제** → 절대값만 쓰지 않고 증가율·상대적 순위·장기 추세를 함께 분석한다.
- **실시간 도시데이터의 지역 제한** → 대상이 주요 120~121개 장소로 한정된다. 서울 전체를 다루는 분석은 파일 데이터(분기/시간 단위)로 수행하고, 실시간은 보조 지표·시연용으로 역할을 분리했다.
- **호출 제한** → 배치 중심 설계로 확정. "파일 데이터를 메인, 실시간은 보조"가 이 계열의 기본 원칙이 됐다.

### 3.2 상권 · 매출 · 점포 계열

| 축 | 검증 결과 |
| --- | --- |
| 사이즈 | 분기 × 상권 × 업종 단위. 행 수 자체는 크지 않으나 여러 데이터의 조인 연산이 무겁다 |
| 형태 | 집계 데이터. **개별 점포 단위가 아니라 상권×업종 집계** |
| 신뢰도 | 추정매출은 **추정** 데이터. 점포·개폐업 수는 공식 집계로 **예측 정답값으로 사용 가능** |
| 시간 범위 | 상권 관련 데이터는 공간 기준의 일관성을 위해 주로 **2021년 이후** 자료 제공 |
| 접근성 | 서울 열린데이터광장에서 즉시 다운로드 |
| 판정 | ✅ |

**확인된 제약과 대응**

- **집계 데이터라 개별 점포 폐업 예측 불가** → 예측 대상을 상권×업종 단위의 전체 폐업률 또는 고위험 확률로 재정의했다.
- **2021년 이후로 시간 범위 제한** → 학습 2021~2023 / 검증 2024 / 테스트 2025로 시간 순 분할. 실제 제공 범위와 결측 확인 후 조정한다는 단서를 달았다.
- **데이터 누수 위험** → t+1분기 폐업을 예측할 때 t+1분기의 매출·점포 수·임대료를 입력 변수로 쓰지 않는다. 무작위 분할 금지.

### 3.3 부동산 · 임대료 계열

**검증 과정에서 가장 많은 제약이 발견된 계열이다.** 임대료 데이터는 "반드시 추가하되, 핵심 데이터와 동일하게 취급하지 않는다"는 결론에 이르렀다.

#### 3.3.1 한국부동산원 임대동향조사 계열 ⚠️

| 축 | 검증 결과 |
| --- | --- |
| 신뢰도 | **표본조사** 기반 평균값. 개별 점포의 실제 계약 임대료가 아니다 |
| 산정 방식 | 보증금과 월세를 환산한 금액을 임대가능면적으로 나누어 산정. **표본이 변경되면 절대값이 흔들린다** |
| 공간 기준 | **서울시 골목상권 경계 ≠ 한국부동산원 조사 상권 경계** |
| 커버리지 | 모든 골목상권의 임대료가 제공되지는 않는다 |
| 파생 계산 한계 | 점포별 면적·관리비를 알 수 없어 실제 임대료 부담률을 정확히 계산할 수 없다 |

**대응 설계**

| 제약 | 대응 |
| --- | --- |
| 표본 변경에 따른 절대값 변동 | 임대료 절대값 대신 **임대가격지수의 변화율**을 우선 활용 |
| 공간 경계 불일치 | ①상권명·행정구역 우선 연결 → ②중심 좌표와 조사 권역 공간 결합 → ③**연결 정확도가 낮은 상권은 임대료 위험 미산정** |
| 커버리지 부족 | **기본 모델 / 임대료 확장 모델 2트랙 분리.** 연결 불가 상권은 수요·경쟁 위험만 제공하고 임대료 위험은 "데이터 부족"으로 표시 |
| 부담률 산출 불가 | "수익성", "임대료 부담률"을 확정적으로 제시하지 않고 **"임대료 압박 신호"** 라는 방향성 지표로 표현 수위 조절 |
| 인과관계 확인 불가 | 아래 표현 규정 적용 |

> **사용하지 않을 표현** — 유동인구 증가 때문에 건물주가 임대료를 올렸고 점포가 폐업했다.
> **사용할 표현** — 유동인구 증가 이후 임대료 상승과 점포당 매출 하락이 함께 나타난 상권에서 다음 분기 폐업률이 높아지는 패턴이 관찰됐다.

**임의 보간을 하지 않는다**는 원칙도 여기서 나왔다 — 임대료가 연결되지 않는 상권에 주변 상권의 값을 복사하지 않는다.

#### 3.3.2 국토부 실거래가 계열 ⚠️

| 축 | 검증 결과 |
| --- | --- |
| 사이즈 | 매매 1,500만~2,000만 건 + 전월세 2,500만~3,000만 건 + 연립다세대·오피스텔 수백만~천만 건 = **합계 약 5,000만 건. 조사한 데이터 중 원본 볼륨 최대** |
| 형태 | **거래 건별 raw 데이터.** 집계 가공본이 아니라 증강 없이 그대로 쓸 수 있다 |
| 신뢰도 | 공식 신고 기반. 단 **이상 거래의 정답 라벨은 존재하지 않는다** |
| 컬럼 제약 | 개인정보 보호로 동·호수, 거래 당사자 정보 미제공 → "같은 물건"을 특정할 수 없다 |
| 접근성 | 시군구(약 250개) × 월 × 거래 유형 단위 API 호출. **일일 호출 제한**으로 전국 20년치 확보에 시간이 걸린다 |
| 시간 범위 | 매매 2006~, 전월세 2011~. **해제 필드는 2021년 이후만 제공** |

**대응 설계**

| 제약 | 대응 |
| --- | --- |
| 일일 호출 제한 | 1주 차에 즉시 수집 시작, 운영계정 승급 신청, 팀원 키 분산 |
| 물건 식별 불가 | 단지+전용면적+층으로 근사 식별. **한계를 발표에 명시하고 매칭 규칙의 오차 분석을 포함** |

### 3.5 대중교통 계열 — 지하철 승하차 데이터의 증강 검증

**"데이터가 분산 처리에 부적합하다"는 사실을 먼저 확인하고, 그 부적합을 정면으로 다룬 사례다.**

| 축 | 검증 결과 |
| --- | --- |
| 사이즈 | **약 8.4만 행** |
| 형태 | 월별 × 호선 × 지하철역 기준, 04시~익일 03시까지 24시간대 승·하차 컬럼 구성. **'월 누적치' 형태의 집계 가공본** |
| 문제 진단 | 원문: "이대로는 단일 PC(Pandas)로 1초 만에 끝나 **분산 처리(하둡/스파크)를 도입할 명분이 부족**하다" |
| 신뢰도 | 공식 통계이나 원시 로그가 아니므로 **세분화 방향의 역산만 가능** |
| 접근성 | 즉시 다운로드 |
| 판정 | ⚠️ — 증강을 전제로만 활용 가능 |

**증강 로직과 무결성 검증 설계**

```
[원본 8.4만 행]
  └─▶ (1단계: 평일/주말 30일 분배) ─▶ [일별: 240만 행]
        └─▶ (2단계: 60분 연속 보간) ─▶ [최종: 1억 4,400만 행 / 약 15~20GB]
```

| 단계 | 로직 | 무결성 보장 장치 |
| --- | --- | --- |
| **1단계** (8.4만 → 240만) | 월 총합을 30으로 균등 분할하지 않고, 평일 22일에 높은 계수·주말 8일에 낮은 계수를 곱해 일자별 총량 산출. 일별 변동성 반영을 위해 약 ±5%의 정규분포 노이즈 적용 | **30일 치를 모두 합산하면 정확히 원본의 한 달 총량이 복원**되도록 보정 계수 적용 |
| **2단계** (240만 → 1억 4,400만) | T-1, T, T+1 시간대를 잇는 연속 슬로프(선형/스플라인)를 생성해 00~59분 60개 슬롯에 단조 증가/감소 형태로 배분 | **60개 분 데이터의 합 = 해당 1시간 총량과 정확히 1:1 일치(질량 보존)** |

**증강의 대외 정당성** — 8/20 컨설턴트미팅에서 별도 질의해 확인했다.

> "신입이라는 특성상 환경보다는 '이만큼 해봤다' 정도면 충분하다."
> "프로젝트를 진행한다면 증강이 어찌 됐든 필요하다."

**남은 검토 과제** — 증강 데이터로 학습한 예측 모델의 성능은 결국 증강 로직에 넣은 가정(평일/주말 가중치, 보간 곡선)을 재현하는 성격이 강하다. 따라서 **모델 성능을 실측으로 검증할 방법이 없다.** 발표 시에는 예측 정확도가 아니라 파이프라인 처리 성능을 전면에 두는 편이 안전하다.

#### 3.7.1 공공자전거 데이터 ✅ — 검증 가능성이 확보된 유일한 조합

| 축 | 검증 결과 |
| --- | --- |
| 사이즈 | 대여이력 연간 수천만 건 |
| 형태 | 대여/반납 시각·대여소·이용거리를 포함한 **건별 이력** |
| 신뢰도 | **실사용 이력(전수).** 추정 데이터가 아니다 |
| 접근성 | 파일 데이터로 로그인 후 즉시 다운로드 |
| **검증 가능성** | **이 계열의 결정적 강점** — 아래 참조 |
| 판정 | ✅ |

공공자전거는 **대여 이력(실사용) 데이터가 공개된 시설**이라, 입지 추천 모델의 타당성을 실제 이용률로 **백테스트**할 수 있다. 무더위 쉼터·공공와이파이 등 이용량 데이터가 없는 시설로 확장하기 전에 검증된 모델을 확보하는 순서가 방법론적으로 가장 견고하다.

**데이터 수급 절차와 착수 순서** — 이 계열은 조사 단계에서 절차까지 구체화한 유일한 사례다.

| 단계 | 내용 |
| --- | --- |
| 접근 절차 | 파일 데이터는 로그인 후 즉시 다운로드. **API류는 활용 신청 후 자동 승인(즉시~1일)이므로 초기에 미리 신청** |
| 착수 1 | 대여이력 1개월치 + 생활인구(행정동 단위) 1개월치 확보 |
| 착수 2 | **스키마·용량·조인 키(날짜, 행정동코드) 확인** |
| 착수 3 | 이상 없으면 집계구 단위 + 다년치로 확장, 집계구 경계 shp 확보 |
| 착수 전 체크 | 샘플 1~3개월치로 **용량·컬럼 스키마·결측** 확인 |
| 규모 리스크 대응 | 예상보다 작을 경우 여러 연도 누적 + 집계구 단위 사용으로 볼륨 확보 |

#### 3.7.2 전기차 충전소 데이터 ⚠️ — 신뢰도 문제를 주제로 전환한 사례

| 축 | 검증 결과 |
| --- | --- |
| 사이즈 | 전국 수만 기 × 주기 폴링 → 축적 시 스트림 볼륨 확보 가능. 배치가 아닌 지속적 스트림 처리 구조가 자연스럽다 |
| 형태 | 충전소/충전기 상세정보 + **상태정보(상태, 상태갱신일시, 마지막 충전 시작·종료일시)** |
| **신뢰도** | **운영사마다 API 상태값 갱신 주기·방식이 제각각이라 "실시간" 표기와 실제 최신성 사이에 괴리가 발생한다** |
| 접근성 | 한국환경공단 API는 **개발계정 기준 트래픽 1,000건**, 활용사례 등록 시 증설 가능 |
| 판정 | ⚠️ — 호출 한도 증설이 전제 |

이 계열에서 신뢰도 문제는 **극복 대상이 아니라 주제 그 자체**가 됐다. 상태값의 부정확성을 문제로 삼고, **상태갱신일시를 신뢰도 판정 피처로 역이용**한다 — API상 "사용가능"인데 상태갱신일시가 임계치 이상 오래됐거나 동일 충전기가 짧은 시간 내 상태값을 비정상적으로 자주 반복하면 이상치로 플래깅해 "진짜 사용가능" 스코어로 보정하는 설계다.

민간 운영사 API는 개별 제휴가 필요해 ❌ 판정을 받았고, **MVP는 공공 데이터만으로 검증한 뒤 민간 제휴로 커버리지를 넓히는** 단계 설계로 정리했다.

### 3.11 네트워크 계열 ❌

**원천이 막혀 있다는 사실을 확인한 뒤, 대안 경로를 설계하고 그 대안의 한계까지 정량화한 사례다.**

| 축 | 검증 결과 |
| --- | --- |
| **원천 접근성** | 원문: "기지국 원본 데이터는 통신사 계약상 **정부기관도 받지 못할 만큼 폐쇄적**이다" → 확보 불가 |
| 대안 경로 | AP 정보는 통신사·소유주의 별도 허락 없이도 확보 경로가 있다. 단 "AP에 붙은 모든 기기"가 아니라 **"AP에 붙은 기기 중 우리 앱 사용자"** 로 범위가 한정된다 |
| **신뢰도 — 표본 문제** | 전수조사가 아닌 표본조사다. "같은 AP에 실제로는 100명이 붙어있어도 우리 앱 사용자가 5명이라면, 우리가 보는 건 그 5명의 리포트뿐이다" → **콜드스타트 문제** |
| 베이스라인 확보 기간 | 이상탐지 베이스라인 학습에 **최소 1~2주의 정상 패턴 축적 기간**이 필요하다 |
| 사업 구조 제약 | 타 통신사·타 Wi-Fi 추천은 사업자 간 제휴 또는 데이터 개방이 필요하다 |
| 판정 | ❌ — 프로젝트 기간 내 유효 표본 확보 불가 |

**설계한 검증 규칙 (다른 계열에도 재사용 가능)**

| 규칙 | 내용 |
| --- | --- |
| 표본 신뢰도 필터 | 최소 리포트 수(예: 5건) 미만인 AP는 **"정보 부족"으로 표시하고 혼잡도를 단정하지 않는다** |
| 프라이버시 하한선 | "몇 명이 접속해 있다"는 개인 식별 불가능한 집계 통계라 법적 소지는 낮으나, 특정 소규모 공간(회의실 등)에서는 인원수 자체가 민감할 수 있어 **최소 10명 이상 밀집 구간**으로 표시 단위를 제한 |
| 탐지 불가 영역 명시 | 패킷 내용 기반 공격(MITM 콘텐츠 변조, DNS 스푸핑 응답 내용)은 딥패킷 인스펙션 수준 접근이 필요한데, 이는 프라이버시·OS 정책상 일반 앱에 허용되지 않는다 |
| 오탐 관리 | 표본 수가 적은 AP는 오탐 위험이 크고, 사용자 신뢰에 직결되는 알림(Evil Twin 경고 등)은 임계값을 보수적으로 설정 |

## 4. 반복해서 부딪힌 검증 이슈

계열을 가로질러 반복된 문제들이다.

### (a) 데이터 규모 부족 vs 분산 처리 명분

| 데이터 | 규모 문제 | 대응 |
| --- | --- | --- |
| 지하철 승하차 | 원본 8.4만 행 — "단일 PC로 1초 만에 끝난다" | 통계 무결성 보존 2단계 증강으로 1억 4,400만 행 확보 |
| 응급·의료 조회형 API | 호출 단위 응답이라 그 자체로 볼륨 없음 | 주기 폴링으로 상태 이력 축적 |
| 제조 공개 데이터셋 | 데이터셋 단위 | 증강 + 분산 설계 경험 자체에 가치 부여 |
| 생활인구 (공공시설 입지) | 예상보다 작을 가능성 | 다년치 누적 + 집계구 단위 사용 |
| 국토부 실거래가 | 원본은 크지만 "빅데이터 대비 작다"는 지적 예상 | **연산 집약 설계(자기 조인·공간 조인) + 워커 수별 성능 실험으로 정면 대응** |
| 재난 API | 이벤트 발생 기반이라 유입량 희소 | 대응안 없음 → 소거 |

### (b) 데이터 접근의 폐쇄성

| 대상 | 벽 | 대응 |
| --- | --- | --- |
| 통신사 기지국 데이터 | 계약상 정부기관도 확보 불가 | 크라우드소싱 대안 → 콜드스타트로 실패 |
| tmap 등 도로 혼잡 데이터 | 확보 경로 없음 | 공공 데이터(TOPIS·도로공사)로 대체 |
| 민간 충전 운영사 | 개별 제휴 필요 | MVP는 공공 API만으로 검증 후 확장 |
| 서울 빅데이터캠퍼스 택시 | 현장 이용·반출 제한 | 뉴욕 TLC로 대체 가능하나 스토리 괴리 |
| 한국환경공단 충전소 API | 개발계정 1,000건 | 활용사례 등록으로 증설 신청 |
| 국토부 실거래가 API | 일일 호출 제한 | 1주 차 즉시 수집 시작, 운영계정 승급, 팀원 키 분산 |
| 서울시 실시간 API류 | 호출 제한 | 파일 데이터를 메인, 실시간은 보조 |

**교훈** — 데이터의 존재 여부와 확보 가능 여부는 별개다. "이런 데이터가 있다"에서 멈추지 않고 **"우리가 5주 안에 실제로 받을 수 있는가"** 까지 확인하는 절차가 필요했고, 이후 이 확인이 스크리닝 1차 관문이 됐다.

### (c) 추정 · 표본 데이터의 신뢰도

핵심 데이터 상당수가 전수가 아니었다.

| 데이터 | 성격 | 대응 |
| --- | --- | --- |
| 서울 생활인구 | 통신 데이터 기반 **추정** | 절대값 대신 증가율·상대 순위·장기 추세 |

## 5. 검증에서 도출된 원칙

개별 데이터를 검증하며 만든 장치들이 계열을 넘어 일반화됐다. **후보 주제가 바뀌어도 그대로 적용할 수 있는 원칙들이다.**

### 원칙 1. 표본이 부족한 구간에는 값을 채우지 않는다

- 임대료가 연결되지 않는 상권에 **주변 상권의 값을 임의로 복사하지 않는다** → "데이터 부족"으로 명시 표시
- 최소 리포트 수(5건) 미만인 AP는 **혼잡도를 단정하지 않는다** → "정보 부족"으로 표시
- 커버리지가 갈리면 **기본 모델 / 확장 모델로 트랙을 분리**하고, 확장 모델의 기여도를 별도 검증한다

### 원칙 2. 추정 데이터는 절대값이 아니라 변화율로 쓴다

생활인구·추정매출·임대료가 모두 추정 또는 표본이다. 절대값은 표본 구성에 따라 흔들리므로 **증가율·상대적 순위·장기 추세**를 분석 단위로 삼는다. 한국부동산원 임대료는 특히 표본 변경 영향을 줄이기 위해 **임대가격지수의 변화율**을 우선한다.

### 원칙 3. 인과관계를 단정하지 않는 표현을 미리 정한다

공개데이터만으로는 개별 인과를 확인할 수 없다. **사용할 표현과 사용하지 않을 표현을 문서에 명시**해 두고, 산출물의 문구까지 그 규정을 따른다. 데이터로 확인 가능한 것은 "패턴이 함께 관찰됐다"까지다.

### 원칙 4. 산출 불가능한 지표는 이름을 바꾼다

점포별 면적·관리비·인건비를 알 수 없으면 "임대료 부담률"이나 "수익성"을 계산할 수 없다. 이때 근사치를 만들어 같은 이름으로 부르지 않고, **"임대료 압박 신호"** 처럼 정확도 수준에 맞는 이름을 붙인다.

### 원칙 5. 증강은 질량 보존을 검증한다

증강 데이터를 쓸 때는 **합산하면 원본 총량이 정확히 복원되는지**를 각 단계마다 확인한다. 지하철 증강의 경우 1단계는 30일 합산 = 월 총량, 2단계는 60분 합산 = 1시간 총량이 되도록 보정 계수를 적용했다. 다만 **증강 데이터로 학습한 모델의 성능은 실측 검증이 불가능**하다는 한계를 함께 인지한다.

### 원칙 6. 착수 전에 샘플로 스키마·용량·결측·조인 키를 확인한다

전체 다운로드 전에 **1~3개월치 샘플**로 용량·컬럼 스키마·결측을 확인하고, 데이터 간 **조인 키(날짜, 행정동코드 등)를 첫 주에 확정**한다. 이상이 없을 때만 다년치·세밀 단위로 확장한다.

### 원칙 7. 접근 제약은 데이터 속성이 아니라 일정 리스크로 다룬다

일일 호출 제한은 "쓸 수 있다/없다"의 문제가 아니라 **"언제까지 다 받을 수 있는가"** 의 문제다. 따라서 대응도 일정 관점이다 — 1주 차 즉시 수집 시작, 운영계정 승급 신청, 팀원 키 분산, 활용사례 등록을 통한 한도 증설.

### 원칙 8. 접근성이 좋다는 것과 적합하다는 것은 다르다

재난 API(USGS·EONET·GDACS)는 인증 부담이 전혀 없어 접근성이 최상이었지만, 이벤트 발생 기반이라 유입량이 희소해 스트리밍·분산 명분이 서지 않았다. **6축을 모두 통과해야 ✅이며, 한 축이 뛰어난 것이 다른 축을 상쇄하지 않는다.**
