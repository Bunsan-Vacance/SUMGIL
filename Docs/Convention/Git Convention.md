# Git 브랜치 전략 및 협업 컨벤션

## 1. 개요

본 문서는 팀의 Git 사용 규칙을 정의합니다. 목표는 다음과 같습니다.

- 브랜치 관리 기준을 통일해 충돌과 혼란을 줄인다
- 코드 리뷰를 통해 품질을 보장하고 지식을 공유한다
- 배포 가능한 상태의 코드를 항상 유지한다

---

## 2. 브랜치 전략 — GitHub Flow

GitHub Flow를 채택합니다. 브랜치는 아래 4종류로 구성됩니다.

| 브랜치 | 역할 | 생명주기 |
| --- | --- | --- |
| `main` | 배포(운영) 가능한 상태만 유지 | 영구 |
| `develop-{team}` | 다음 릴리즈를 위한 통합 개발 브랜치(각 파트 BE, FE, AI 별로 존재) | 영구 |
| `feat/{스토리 prefix}-*` | 기능 개발(스토리) 단위 작업 브랜치(각 파트의 develop 브랜치에서 분기) | MR 병합 후 삭제 |
| `feat/{작업내용}` | 특정 스토리에 속하지 않는 예외 작업 브랜치 | MR 병합 후 삭제 |
| `hotfix/*` | 운영 중 긴급 버그 수정(main 브랜치에서 분기) | 수정 완료 후 삭제 |

### 브랜치 흐름

```
main     ──────────●─────────────────────●───────────────●──▶
                   \                   / \             /
                    \                 /   (hotfix 반영)
develop(BE, FE, AI)  ──●───●───●───●───●───●─┴─────●───●───●──▶
                        \       \       /         /
feat/*                ●───●───┘       ●───●───┘
```

- `feat/*`는 `develop`에서 분기해 `develop`으로 병합
- `hotfix/*`는 `main`에서 분기, 수정 후 `main`과 `develop` 양쪽에 병합

### 이슈 계층 구조: 에픽 > 스토리 > 작업

- 기능 개발은 **에픽(Epic) → 스토리(Story) → 작업(Task)** 순으로 세분화됩니다.
- **에픽과 스토리는 닫지 않습니다.** 진행 상황을 묶어서 추적하는 상위 단위로만 사용하며, 하위 작업이 모두 끝나도 자동으로 종료되지 않습니다. (필요 시 팀 논의 후 수동으로 종료)
- 실제로 완료(Done) 처리되는 단위는 **작업(Task)** 이슈이며, 브랜치는 스토리 기준으로 생성하되 커밋 및 MR의 관련 이슈에는 작업 이슈 키를 사용합니다.

### 브랜치 네이밍 규칙 (스토리 단위)

```
feat/{스토리 prefix}-{작업 내용}     예) feat/AUTH-001-login-api
hotfix/{이슈번호}-{작업내용}     예) hotfix/215-payment-error
```

- 이슈번호는 JIRA 이슈 키를 사용 (예: `S15P21A1-23`)
    - 브랜치는 작업이 아닌 **작업이 속한 스토리**의 키를 사용 (에픽 키 아님)
- 작업내용은 영문 소문자 + 하이픈(-), 한 줄로 무엇을 하는지 알 수 있게 작성
- `main`, `develop`은 직접 커밋 금지 — 반드시 MR을 통해서만 반영

## 3. MR(Merge Request) 및 코드 리뷰 규칙

### 3.1 기본 원칙

- **모든 `feat/*` 작업은 `develop`으로** M**R을 생성**하며, 직접 push는 금지합니다
- **MR은 원칙적으로 작업(Task) 단위로 생성**합니다 (스코프가 작고 서로 유관한 작업 2개 정도까지는 예외적으로 묶어서 진행 가능 — 자세한 내용은 3.3 참고)
- **리뷰어 1인 이상의 승인(Approve)** 을 받아야 병합할 수 있습니다
- 작성자 본인은 승인 카운트에 포함되지 않습니다
- 승인 후에도 논의 중인 코멘트(unresolved)가 있으면 병합하지 않습니다

### 3.2 Issue 템플릿

- Jira 에서 이슈 생성 후 브랜치 만들기 → git lab에 자동 브랜치 생성

### 3.3 MR 템플릿

#### 타이틀

```markdown
[에픽 code(prefix)] 작업 타이틀

ex) [INFRA] AI 개발 환경 구축
		[CHAT] 채팅 agent 아키텍처 구현
		[DEPLOY] develop-BE → main
		- 메인에 배포
		[SYNC] main → develop-AI
		- 메인-디벨롭 동기화 
```

```markdown
## 작업 내용
- 무엇을 했는지 요약

## 스토리
- `S15P21A104-##`

## 관련 이슈
- Closes `S15P21A104-##`
- Closes `S15P21A104-##`

## 변경 사항
- [ ] 주요 변경점 1
- [ ] 주요 변경점 2

## 테스트
- 어떻게 테스트했는지 (선택)
```

- **스토리**: 브랜치명에 사용한 스토리 키를 그대로 기입
- **관련 이슈**: **작업(Task) M개로 MR 1개**를 생성하며, 관련 이슈에는 해당 작업 이슈 키를 모두 입력
    - 단, **Task** 볼륨이 너무 커지지 않도록 유의

### 3.4 리뷰 가이드

- **24시간 이내** 1차 리뷰 응답을 원칙으로 함 (리뷰 병목 방지)
    - 같은 역할의 팀원이 Approve.
    - 응답이 24시간 이내 불가 : 진행
- 리뷰어는 아래 관점을 확인:
    - 요구사항/이슈 내용과 일치하는가
    - 컨벤션(네이밍, 포맷)을 지켰는가
    - ~~테스트 코드가 필요한 부분에 있는가~~
    - ~~예외 처리, 엣지 케이스를 고려했는가~~

### 3.5 머지 방식

- **Merge** 를 기본으로 사용 (feat 브랜치의 잡다한 커밋을 하나로 정리)
- 병합 후 원격 `feat/*` 브랜치는 삭제

## 4. 커밋 메시지 컨벤션 (JIRA 연동, 작업 단위)

커밋 메시지 맨 앞에 **JIRA 이슈 키**를 붙여 Conventional Commits와 결합합니다.

```
[<JIRA-KEY>] <type>: <subject>
```

**type 종류**

| type | 의미 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 포맷팅, 세미콜론 등 (로직 변경 없음) |
| `refactor` | 리팩토링 (기능 변화 없음) |
| `test` | 테스트 코드 추가/수정 |
| `chore` | 빌드, 설정, 패키지 매니저 등 |

**예시**

```
[S15P11A108-23] feat: 카카오 로그인 API 연동
[S15P11A108-31] fix: 장바구니 수량 0일 때 삭제 안 되는 버그 수정
[S15P11A108-12] docs: 실행 방법 섹션 추가
```

- subject는 한글 기준 50자 이내, 명령형/서술형 통일 (팀 내 택1)
- 이슈 키는 대괄호 `[ ]`로 감싸서 맨 앞에 위치 — JIRA가 이슈 키를 인식하는 표준 패턴이라 가장 안전함

## 5. JIRA-Git 연동 설정 (필수 사전 작업)

브랜치명이나 커밋 메시지에 이슈 키를 적는 것만으로는 아무 일도 일어나지 않습니다. **저장소를 JIRA에 연결**해야 위 규칙들이 실제로 동작합니다.

1. JIRA 프로젝트 설정 → 앱(Apps) → 사용 중인 Git 호스팅에 맞는 앱 설치
    - ~~GitHub 사용 시: GitHub for Jira~~
    - GitLab 사용 시: **GitLab for Jira**
    - Bitbucket 사용 시: 기본 내장 연동 (별도 설치 불필요)
2. 연동할 조직/저장소를 선택하고 권한 승인
3. 연동이 끝나면 이슈 상세 화면의 **"개발(Development)"** 탭에 관련 브랜치·커밋·MR이 자동으로 표시됨

**연동(linking)과 자동화(automation)는 별개로 동작합니다.**

| 구분 | 필요한 것 | 결과 |
| --- | --- | --- |
| 연동만 | 브랜치명에 이슈 키 포함 (이미 본 문서의 브랜치 네이밍 규칙으로 충족) | 개발 탭에 커밋/MR 표시 |
| 자동화까지 | 커밋 메시지에 이슈 키 + Smart Commit 명령어 | 이슈 상태·댓글·작업시간 자동 반영 |

---

## 6. 핫픽스 프로세스

**핫픽스**

1. `main`에서 `hotfix/{이슈번호}-{내용}` 분기
2. 긴급 수정 후 MR 생성 (리뷰어 2인 이상 승인)
    1. BE 1 / FE 1 / (AI 1)
3. `main`에 병합
4. `hotfix/*` 브랜치 삭제

## 7. 체크리스트 요약

- [ ]  `main`, `develop` 직접 커밋, 브랜치 삭제 금지
- [ ]  브랜치명은 `feat/이슈번호-내용` 규칙 준수
- [ ]  MR은 `develop` 대상으로 생성(핫픽스인 경우 `main` 대상으로 생성)
- [ ]  리뷰어 1인 이상 승인 후 병합
- [ ]  병합 방식은 Merge
- [ ]  커밋 메시지는 `[JIRA-KEY] type: subject` 형식 준수
- [ ]  저장소-JIRA 연동 앱(GitLab for Jira) 설치 완료
- [ ]  핫픽스는 `main` 반영 확인
- [ ]  브랜치는 스토리 이슈 키 기준 생성 (에픽 아님)
- [ ]  MR은 작업 단위 생성 (유사 작업 2개까지만 예외적 결합 가능)
- [ ]  에픽/스토리는 임의로 닫지 않음
