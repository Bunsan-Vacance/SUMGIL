## 12. k6 부하테스트로 배포 환경 좌표 검색 API가 완전히 마비된 문제

### 부하테스트가 뭔지, k6가 뭔지

**부하테스트**는 "실제 사용자 여러 명이 동시에 몰리면 서버가 버티는지"를 미리
가짜 트래픽으로 확인해보는 작업이다. **k6**는 그 가짜 트래픽을 만들어주는
도구다 — "이 API를 몇 명이 동시에, 얼마 동안 계속 호출해봐"라고 시나리오를
짜주면, 실제로 그만큼 요청을 쏴주고 결과(얼마나 빨리 응답했는지, 실패는 없었는지)를
정리해준다.

**VU(Virtual User, 가상 사용자)**는 "동시에 접속한 사용자 한 명"을 흉내 내는
단위다. VU 30이면 "30명이 동시에 이 API를 계속 호출하고 있다"는 뜻이다.

### 어떤 강도로 테스트했나

- 대상 API: `POST /api/routes/search/coordinate`(좌표를 입력하면 경로를
  찾아주는 API, S15P21A104-154). 이미 만들어져 있던 스크립트
  (`BE/scripts/loadtest/k6-coordinate-search.js`)를 그대로 사용
- 대상 서버: 로컬 개발 서버가 아니라 **실제 배포된 서비스**
  (`https://j15a104.p.ssafy.io`, 팀 전체가 같이 쓰는 환경) — 다른 팀원 작업에
  지장 없는지 미리 확인하고 진행
- **테스트 흐름(k6 용어로 "ramping-vus" — 사용자 수를 서서히 늘렸다 줄이는
  방식)**:
  1. **웜업 20초**: 사용자 0명 → 15명으로 서서히 늘림 (갑자기 확 몰아치면 결과가
     왜곡되니, 서서히 늘려서 정상 상태부터 확인)
  2. **본구간 1분**: 사용자 15명 → 30명까지 늘려서 그 상태를 유지 — 이 구간이
     실제로 측정하려는 "30명이 동시에 몰리면 어떻게 되나"다
  3. **램프다운 20초**: 사용자를 30명 → 0명으로 서서히 줄이며 마무리
  - 총 소요 시간: 1분 50초
- **호출 내용**: 서울 시내 실제 6개 지점(역삼·강남·신촌·잠실·건대입구·홍대입구)
  좌표를 미리 준비해두고, 매번 그중 두 곳을 무작위로 골라 "여기서 저기로 가는
  경로 찾아줘"라고 반복 요청 — 매번 다른 조합이라 캐시로 쉽게 응답하는 상황을
  막고, 실제 사용자들이 서로 다른 곳을 검색하는 상황과 비슷하게 만들었다

### 어떤 결과가 나왔나

k6는 테스트 전에 "이 정도는 통과해야 한다"는 기준(임계값)을 미리 정해두는데,
이번엔 그 기준을 둘 다 크게 못 미쳤다.

| 지표 | 뜻 | 결과 | 통과 기준 |
| --- | --- | --- | --- |
| `http_req_duration` p95 | 전체 요청 중 95%가 이 시간 안에는 응답받았다는 값 (나머지 5%는 더 오래 걸림) | **22.72초** | 2초 미만 |
| `http_req_failed` | 전체 요청 중 실패(에러 응답·타임아웃 등)한 비율 | **84.42%** | 1% 미만 |
| 502 응답 | 서버가 아예 응답을 못 줘서 중간 게이트웨이가 대신 에러를 돌려준 횟수 | 18건 | — |

흥미로운 점: **중앙값(요청 절반이 이 안에 끝난 시간)은 11.39ms로 멀쩡했다.**
그런데 평균은 2.97초, 최악의 경우는 44초까지 걸렸다. 즉 "전체적으로 다
느려진" 게 아니라, **일부 요청만 뭔가에 걸려서 한없이 안 끝나고 있다가 평균을
확 끌어올린** 모양새였다.

그리고 테스트 도중 **백엔드 서버(파드)가 한 번 강제로 재시작**됐다 — 부하테스트
실행 시각과 정확히 겹쳤다.

### 문제 분석을 어떤 방식으로 했나

("파드"는 쿠버네티스에서 서버 프로그램 한 개가 돌아가는 단위라고 보면 된다.)

1. **`kubectl -n prod get pods`** — 지금 떠 있는 서버들 목록을 봄. BE 서버가
   "8분 50초 전에 한 번 재시작됨"이라고 나와서, 부하테스트 시간과 겹치는 걸 확인
2. **`kubectl -n prod describe pod <서버이름>`** — 그 서버가 왜 재시작됐는지
   자세한 이력을 봄. 여기서 두 가지를 확인:
   - **종료 코드가 143이었다** (메모리 부족으로 강제 종료됐으면 137이 찍혔을
     텐데 그게 아니었다 — 그래서 "메모리 부족은 아니다"를 먼저 배제할 수 있었음)
   - **"Liveness probe failed"** — 쿠버네티스가 주기적으로 "너 살아있니?"라고
     서버에 확인 신호(헬스체크)를 보내는데, 그 확인 신호에 응답을 못 해서
     "죽었다"고 판단하고 강제로 재시작시킨 것
3. **`kubectl -n prod logs <서버이름> --previous --tail=200`** — 재시작 **되기
   전**의 로그를 봄(`--previous`를 꼭 붙여야 한다 — 재시작 후엔 그 이전 로그가
   기본으로는 안 보이기 때문)

### 무엇이 문제였나

로그를 뜯어보니 세 가지가 한 번에 겹쳐서 벌어지고 있었다.

1. **정류소 하나 조회할 때마다 새 스레드를 만드는 코드**가 있었다. (`스레드`는
   프로그램이 여러 작업을 동시에 처리하기 위해 쓰는 실행 단위 — 너무 많이
   만들면 컴퓨터가 그거 관리하는 데만 힘을 다 씀.) 좌표 검색 응답에 "이 버스
   혼잡하다"는 정보를 실시간으로 붙여주는 기능(`BusCongestionReader`)이,
   정류소 개수만큼 스레드를 그때그때 새로 찍어내고 있었다 — 개수 제한이
   전혀 없이. 요청이 몰리니까 스레드가 감당 안 될 만큼 계속 늘어났다.
2. 게다가 그 기능이 불러오는 **외부 버스 도착정보 API 자체가 자주 실패하거나
   느렸다** — 로그에 같은 정류소 조회 실패가 수백 번 반복되고, "1.5초 안에
   응답을 못 받았다"는 타임아웃 경고도 많았다.
3. **결정적 증거**: 로그에 이런 줄이 있었다.
   ```
   DB 연결 상태 확인(Health check)에 25.4초가 걸렸다
   ```
   DB에 잠깐 연결해서 "살아있나?" 확인하는 아주 가벼운 작업인데, 이게 25초나
   걸렸다는 건 DB 자체 문제가 아니라 **서버(JVM) 전체가 너무 바빠서 그 가벼운
   작업조차 순서를 못 받고 있었다**는 뜻이다. 스레드가 폭증하면서 컴퓨터가
   "누구 차례로 일할지 정하는 것"(스케줄링)에만 자원을 다 쓴 셈이다.

결과적으로: 스레드 폭증 → 서버 전체가 버벅임 → 쿠버네티스의 "살아있니?"
확인(1초 안에 답해야 함, 3번 연속 실패하면 재시작)에도 답을 못 함 → 강제
재시작. 재시작 처리 중에도 이미 처리하던 요청들이 응답을 보내려 했지만, 그
사이 k6 쪽은 이미 타임아웃으로 포기하고 연결을 끊은 뒤라 "상대가 이미 끊긴
연결에 쓰려다 실패"(Broken pipe)하는 에러가 대량으로 쌓였다.

**처음 세운 가설(카카오 지도 API 호출이 병목일 것이다)은 로그로 확인해보니
틀렸다.** 실제 범인은 카카오 API가 아니라 버스 혼잡도 조회의 스레드 생성 방식
이었다 — 짐작만으로 결론 내리지 않고 로그를 직접 확인한 게 중요했다.

### 어떤 방식으로 해결하는 게 좋을지

- **가장 우선**: 버스 혼잡도 조회 코드가 스레드를 무제한으로 만들지 않도록,
  **개수 제한이 있는 스레드 풀**을 쓰도록 바꾼다. (자바에서는
  `ExecutorService`/`CompletableFuture`라는 걸 쓰면 "최대 몇 개까지만 동시에
  일하고, 넘치면 순서 기다려라"를 강제할 수 있다.) 이게 근본 원인을 없애는
  방법이다.
- 외부 버스 API가 특정 정류소에서 계속 실패한다면, 그 정류소는 잠깐 조회를
  건너뛰는 "**회로 차단**(서킷 브레이커)" 방식을 검토한다 — 안 될 걸 알면서
  계속 기다리는 낭비를 줄이는 것.
- 쿠버네티스의 "살아있니?" 확인 시간을 늘려주는 것도 방법이긴 한데, 이건
  **증상만 가리는 미봉책**이라 우선순위를 낮게 둔다 — 스레드가 계속 폭증하는
  건 그대로니 결국 다른 방식으로 또 문제가 생길 것이다.
- (여유가 되면) 스레드 개수나 DB 연결 확인 시간을 대시보드에서 바로 볼 수
  있게 모니터링 지표를 추가해두면, 다음에 비슷한 일이 생겼을 때 이렇게 로그를
  하나하나 뒤지지 않아도 된다.

### 교훈

- "느려진 것 같다"는 느낌만으로 짐작한 원인(카카오 API)을 그대로 믿지 않고,
  실제 로그를 순서대로(서버 목록 확인 → 재시작 이력 확인 → 재시작 직전 로그
  확인) 따라간 게 정확한 원인을 찾는 데 결정적이었다.
- 종료 코드 하나(143 vs 137)만 봐도 "메모리 문제인지 아닌지"를 먼저 걸러낼 수
  있다 — 사소해 보이는 정보가 원인 후보를 크게 좁혀준다.
- 로컬에서 해봤던 부하테스트는 외부 API를 안 쓰는 기능들 위주라 이런 문제가
  전혀 안 보였다. **"로컬에서 문제없었다"가 "실제 서비스에서도 문제없다"를
  보장하지 않는다** — 외부 API를 쓰는 기능은 반드시 한 번은 실제 배포 환경에서
  부하를 걸어봐야 한다는 걸 이번에 확인했다.

## 13. 수정 배포 후 재검증 — 마비는 해결, 그 아래 있던 다른 병목이 드러남

항목 12에서 찾은 원인(정류소마다 스레드를 무제한으로 만드는 문제)을 고치고
(S15P21A104-291, `fix/QA-bus-congestion-thread-pool` 브랜치) `develop-BE`에
머지·배포한 뒤, **똑같은 조건으로 k6를 다시 돌려 수정 전/후를 비교**했다.

### 배포됐는지 어떻게 확인했나

MR이 머지됐다고 바로 배포된 게 아니다 — 이 프로젝트는 `develop-BE`에 머지되면
GitLab CI가 **자동으로** 이미지를 새로 만들어 배포하는 구조(`deploy-be` job,
`.gitlab/ci/deploy.yml`)라, 머지 후에도 실제로 배포까지 끝났는지 별도로
확인해야 했다.

```bash
kubectl -n prod get deployment be -o jsonpath='{.spec.template.spec.containers[0].image}'
```
이 명령으로 지금 떠 있는 서버가 쓰는 이미지의 커밋 해시를 확인하고, 그게
방금 머지한 커밋과 일치하는지 봤다. 처음 확인했을 땐 아직 옛날 이미지
(`a3763cef`, 수정 전 커밋)라 "아직 배포 안 됐다"는 걸 알 수 있었고, GitLab
파이프라인이 배포 중인 걸 확인한 뒤 완료를 기다렸다가 다시 부하테스트했다.

### 수정 전/후 결과 비교

| 지표 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 502 응답(서버가 응답을 아예 못 줘서 생기는 에러) | 18건 | **0건** |
| 테스트가 끝까지 정상 진행됐는가 | 도중에 서버가 재시작되며 밀림 | **1분 50초 전 구간 정상 진행** |
| 처리된 총 요청 수 | 456건 | **1,460건** (3배 이상) |
| 서버(파드) 강제 재시작 | 발생함 | **발생함 — 정정, 14번 참고** |
| "성공한" 요청의 응답 시간(평균/p95) | 19.0초 / 34.6초 | 19.4초 / 30.8초 (**거의 그대로**) |
| `http_req_failed`(k6가 실패로 집계하는 비율) | 84.4% | 95.3% (수치만 보면 더 나빠 보임) |

> **정정(2026-09-23):** 이 문서를 처음 쓸 때는 "502가 없고 끝까지 완주했다"는
> 정황만 보고 "재시작 안 됨"이라고 적었는데, 나중에 `kubectl -n prod get pods`로
> 다시 확인해보니 **이번에도 파드가 한 번 재시작됐다**(`RESTARTS: 1`). 정황
> 증거만으로 결론 내린 게 성급했다 — 아래 14번에서 이 재시작을 다시 조사한
> 내용을 남긴다. (결론만 먼저 말하면: 스레드 문제가 재발한 건 아니고, 별개의
> CPU 포화 문제였다. 아래 "새로 드러난 것" 절의 가설 2번이 맞았다.)

### 왜 실패율 수치는 더 나빠 보이는데 "좋아졌다"고 하는가

**VU(Virtual User)**는 k6가 동시 접속자 한 명을 흉내 낼 때 쓰는 단위,
**`http_req_failed`**는 k6가 "이 요청은 실패로 본다"고 집계하는 비율이다
(기본적으로 404 같은 정상적인 응답도 상태 코드가 400 이상이면 일단 "실패"로
집계한다 — 그래서 이 스크립트는 별도로 `200 or 404` 체크를 따로 둔 것).

이번 결과의 핵심은 **실패의 "성격"이 완전히 달라졌다는 것**이다.

- **수정 전**: 서버가 통째로 마비되다가 재시작되면서, 요청들이 응답을 못 받고
  뭉개지거나(502) 아주 오래 걸리다 겨우 성공했다. 서버가 죽었다 살아났다 하는
  중이라 결과 자체가 불안정했다.
- **수정 후**: 서버는 안 죽고 끝까지 버텼다. 다만 **동시에 처리할 수 있는 양보다
  훨씬 많은 요청이 몰리니, 감당 못 하는 요청들은 빠르게 실패 처리되고, 감당되는
  일부만 처리되는데 그마저도 여전히 느리다.** 즉 "천천히 죽어가며 버벅이던 것"에서
  "안 죽고 버티되, 넘치는 요청은 빨리 포기하는 것"으로 바뀐 것 — 서버 입장에서는
  자기 자신을 지키는 훨씬 건강한 실패 방식이다.

정리하면 **"목표로 했던 문제(서버 마비·강제 재시작)는 확실히 해결됐다.**"
실패율 숫자만 보면 나빠 보이지만, 그 숫자가 의미하는 상황 자체가 이전과
완전히 다르다.

### 새로 드러난 것 — 별개의 처리 용량 문제

서버가 안 죽으니, 원래부터 있었지만 마비 증상에 가려져 있던 문제가 보이기
시작했다: **성공한 요청도 여전히 19~30초씩 걸린다.**

버스 혼잡도 조회 코드를 다시 보면, 정류소들을 **동시에(병렬로)** 조회하긴
하지만, 그 결과를 기다리는 부분은 **동기(blocking)** 방식이다 — 즉 요청 하나를
처리하던 스레드가 최대 1.5초 동안 "여기서 멈춰서 기다린다." 이것만으로는 19~30초를
설명하기엔 부족해서, 다음 두 가지를 의심하고 있다.

1. 이 블로킹 시간(최대 1.5초)이 동시 요청 30개가 겹치면서 누적됐을 가능성
2. 경로 탐색 자체가 CPU를 많이 쓰는 연산인데, 서버(파드)의 CPU 제한이 2코어뿐이라
   (`kubectl describe pod`에서 확인한 `Limits: cpu: 2`) 요청 30개가 몰리면 CPU
   순서를 기다리며 밀리는, **스레드 문제와는 별개의 순수한 처리 용량 부족**

### 다음 단계

- 이번 재검증 시점 서버 로그를 다시 확인해 "200/404가 아닌 나머지 96%"가
  구체적으로 어떤 상태(타임아웃인지, 다른 에러인지)로 실패했는지 확인
- CPU 사용률이 실제로 포화 상태였는지 확인(가능하면 리소스 모니터링 지표로)
- 확인 결과에 따라 (a) 요청 처리 방식을 비동기로 바꾸거나, (b) 파드 CPU 자원을
  늘리거나, (c) 동시 처리 가능한 요청 수 자체에 상한을 두는 방안을 검토

### 교훈

- 부하테스트 결과를 "실패율이 올라갔다/내려갔다"는 숫자 하나로만 판단하면 안
  된다. **실패의 성격(어떻게 실패했는가)이 왜 바뀌었는지까지 봐야** 진짜
  좋아진 건지 아닌지 알 수 있다.
- 문제 하나를 고쳤다고 시스템이 완벽해지는 게 아니다 — 여러 문제가 겹쳐 있을
  때는 큰 문제(서버 마비)가 작은 문제(처리 용량 부족)를 가리고 있을 수 있고,
  큰 문제를 걷어내야 비로소 다음 문제가 보인다.
- MR이 머지됐다고 배포가 끝난 게 아니다 — 이 프로젝트처럼 CI가 자동 배포하는
  구조에서도, 실제로 새 이미지가 떴는지는 별도로 확인하는 습관이 필요하다.

## 14. 재시작 재발 원인 확정 — 스레드 문제 재발 아님, CPU 포화가 별개 원인

13번에서 "재시작 안 됨"이라고 적었던 게 틀렸다는 걸 확인한 뒤, 그 재시작이
**12번과 같은 원인(스레드 폭증)이 재발한 건지, 아니면 13번 끝에서 의심했던
별개의 CPU 부족 문제인지**를 가려내는 조사다.

### 재시작 확인

```bash
kubectl -n prod get pods
```
`be-854fccf986-2d5wx` 파드가 `RESTARTS: 1 (10m ago)`로 나왔다 — 재시작이
실제로 있었다는 뜻.

```bash
kubectl -n prod describe pod be-854fccf986-2d5wx
```
- 실행 중인 이미지 태그가 스레드풀 수정 커밋과 일치 — 수정된 코드가 맞게
  떠 있었다는 것부터 확인
- `Last State: Terminated, Reason: Error, Exit Code: 143` — 12번과 **똑같은
  종료 코드**
- `Liveness probe failed: context deadline exceeded`가 반복되다 `Killing` —
  12번과 **똑같은 증상**

여기까지만 보면 "고친 게 하나도 소용없었나?"로 보일 수 있다. 그래서 이번엔
**재시작 되기 전 로그**를 다시 떠서 스레드 이름을 확인했다.

```bash
kubectl -n prod logs be-854fccf986-2d5wx --previous --tail=300
```

### 로그에서 확인한 것 — 스레드는 문제없이 동작 중이었다

로그에 등장하는 스레드 이름이 전부 다음 두 종류뿐이었다.

- `http-nio-8080-exec-N` — 정상적인 요청 처리 스레드
- `bus-congestion-fetch-N` — 12번에서 고치며 만든, **개수가 16개로 제한된
  전용 스레드 풀**의 스레드

12번 사고 때 나타났던 `Thread-317`처럼 이름에 숫자만 붙은, 제한 없이
찍어낸 스레드는 **단 한 줄도 없었다.** 즉 **스레드 풀 수정은 정확히 의도대로
작동하고 있었다** — 이번 재시작의 원인이 아니다.

다만 로그에는 이번에도 다음 줄이 있었다.
```
Health contributor org.springframework.boot.jdbc.health.DataSourceHealthIndicator (db) took 12560ms to respond
```
(다른 시점엔 15730ms, 17456ms, 10536ms까지도 나왔다.) DB 살아있는지
확인하는 가벼운 작업이 10~17초씩 걸렸다는 건 12번과 마찬가지로 "서버가 너무
바빠서 가벼운 작업조차 순서를 못 받고 있었다"는 신호다. 스레드 개수는
문제없는데도 이런 지연이 나온다는 게, "그럼 스레드가 아니라 CPU 자체가
부족한 것 아닌가"라는 다음 가설로 이어졌다.

### CPU 사용률 직접 확인

```bash
kubectl -n prod top pod -l app=be
```
을 부하테스트 도중 반복 조회해보니, 값이 `1994m → 2001m → 1993m`처럼
**정확히 2000m(2코어) 근처에 딱 붙어서 몇 분간 유지**됐다. 이건 그 파드에
걸린 CPU 상한(`limits.cpu: 2000m`, `BE/k8s/prod/be.yaml`)에 완전히 막혀서
더 못 올라간 것이다 — 즉 **이 파드는 CPU가 100% 포화 상태였다.**

CPU가 꽉 차면 OS가 어떤 스레드에도 실행 시간을 충분히 못 준다. 경로
탐색이든 헬스체크용 DB 핑이든 전부 순서를 기다려야 하고, 그래서 트리비얼한
헬스체크마저 10~17초씩 걸렸고, Liveness probe(1초 제한)가 반복 실패해
파드가 죽었다 — **12번과 증상은 똑같지만 원인은 완전히 다른 문제**였다.

### 결론

이번 재시작은 두 문제가 증상은 같고(Exit 143·probe 타임아웃) 원인은 다른
경우다.

| | 12번(최초) | 14번(재발) |
| --- | --- | --- |
| 증상 | Exit 143, Liveness probe 타임아웃 | 동일 |
| 원인 | 스레드 무제한 생성 (`Thread-N`) | **CPU 100% 포화** (스레드는 정상) |
| 증거 | 로그의 `Thread-317` 등 이름 없는 스레드 | `kubectl top pod`가 2000m에 고정됨 |
| 상태 | 해결됨(스레드 풀로 제한) | 별개 작업 필요 |

### 교훈

- **증상이 같다고 원인이 같다고 단정하면 안 된다.** Exit 143·Liveness
  타임아웃은 "서버가 뭔가에 막혀서 응답을 못 했다"는 결과일 뿐, 그 앞에
  스레드 폭증이 있었는지 CPU 포화가 있었는지는 매번 다시 확인해야 한다.
- 이번엔 **스레드 이름 패턴**(`Thread-N` vs `bus-congestion-fetch-N`)이 두
  원인을 가르는 결정적 단서였다 — 고친 코드가 실제로 의도대로 동작하는지를
  "재시작이 없다/있다"가 아니라 이런 구체적인 흔적으로 확인해야 한다.

## 15. CPU 상한 2 → 3코어 증설 실험 — 안정성은 해결, 속도는 여전히 부족

14번에서 CPU 포화가 원인으로 확정된 뒤, **파드의 CPU 상한을 2코어에서
3코어로 올리면 얼마나 나아지는지** 실측했다.

### 3코어로 올려도 되는 근거부터 확인

CPU를 무작정 올리기 전에, 그 파드가 떠 있는 워커 노드 자체에 여유가
있는지부터 봤다.

```bash
kubectl describe node ip-172-26-10-6
```
- `Capacity: cpu: 4` — 이 노드는 물리적으로 **4코어**다
- `Allocated resources` — 지금 그 노드에서 도는 모든 파드(Postgres·Redis·
  FE·수집기류 포함)가 예약(request)해 쓰는 CPU 합계가 **950m(23%)뿐**

즉 BE의 "2코어 상한"은 하드웨어 제약이 아니라 `BE/k8s/prod/be.yaml`에
직접 적어둔 숫자였고, 노드에는 아직 손 안 댄 CPU가 넉넉히 남아 있었다.
3코어로 올려도 같은 노드의 다른 서비스(Postgres·Redis 등)를 굶기지 않을
여유가 있다고 판단했다.

> **참고 — 아직 코드로 반영 안 됨.** 이번 실험의 3코어 상향은 클러스터에
> 직접(운영 중 변경) 적용한 것이고, `BE/k8s/prod/be.yaml`의 `limits.cpu`
> 값은 아직 `2000m` 그대로다(git 확인 완료, `develop-BE` 최신도 동일).
> 즉 다음에 CI가 이 파일 그대로 재배포하면 **조용히 2코어로 되돌아간다.**
> 실험 결과가 만족스러우면 이 값을 YAML에도 반영해 IaC와 실제 상태를
> 맞춰야 한다.

### 테스트 방법

12번과 완전히 같은 조건(같은 k6 스크립트, VU 0→15→30, 웜업 20초+본구간
1분+램프다운 20초)으로 CPU만 2코어 → 3코어로 바꿔서 두 번 돌렸다(두 번째는
같은 3코어 조건에서 재확인 차 다시 돌린 것 — 코드나 설정 변경 없음).

### 결과

| 지표 | 2코어(12·13번) | 3코어 1차 | 3코어 2차 |
| --- | --- | --- | --- |
| 처리량 | 456건 | 118건 | 193건(1.83/s) |
| `http_req_failed` | 84.4%~95.3% | **0.00%** | **0.00%** |
| 502 응답 | 18건(2코어 최초) | **0건** | **0건** |
| p95 응답 시간 | 30.8초 | 41.74초 | 21.41초 |
| 평균 응답 시간 | 19.4초 | 13.7초 | 8.88초 |
| 파드 강제 재시작 | 발생(둘 다) | 확인 안 함 | 확인 안 함 |

(2코어 열의 처리량 456건은 12번 최초 결과다. 13번 재검증 때는 1,460건까지
처리했지만 그건 이미 스레드 풀 수정이 들어간 뒤라 이번 비교와 조건이
달라 표에서 뺐다.)

### 분석

**좋아진 것 — 안정성.** 실패율이 완전히 0%로 떨어졌고 502도 사라졌다.
이건 명확한 개선이다.

**안 좋은 것 — 속도.** p95가 여전히 기준(2초)의 10~20배다. 3코어로도 30명
동시 요청의 CPU 수요를 다 못 받아내는 건 마찬가지고, 다만 이제는 죽는 대신
다들 오래 기다리는 쪽으로 증상이 바뀐 것뿐이다.

**같은 조건인데 1차·2차 결과가 다른 이유.** 코드·설정 변경이 전혀 없는
두 번의 3코어 테스트인데도 처리량·응답시간이 꽤 차이 난다(p95
41.74초 → 21.41초). 가장 유력한 설명은 **JVM 워밍업**이다 — 1차 테스트
직후 JIT 컴파일·커넥션 풀 등이 데워진 상태에서 2차를 곧바로 이어 돌렸을
가능성이 크다. 이 차이를 "성능이 개선됐다"고 해석하면 안 되고, **같은
조건에서도 이 정도 폭으로 결과가 흔들릴 수 있다**는 뜻으로 받아들이는 게
맞다.

**아직 반영 안 된 변수.** 이 두 테스트 모두 스레드풀 수정(12번 대응) 이후,
그러나 **동시 처리 상한(세마포어, S15P21A104-291 커밋 `ed42aa5`)은 아직
배포 전** 상태에서 돈 것이다. 세마포어가 배포되면 p95 자체가 좋아지진
않겠지만(허용된 4개 슬롯 안에서 오래 걸리는 건 동일), 초과 요청이 무한정
기다리는 대신 빠르게 503을 받게 되어 실패 양상이 또 한 번 바뀔 것으로
예상한다 — 다음 실험 대상이다.

### 결론

- CPU 증설(2→3코어)만으로 **"안 죽는다"는 확실히 해결됐다.**
- 그러나 **"쓸 만한 속도로 응답한다"는 여전히 해결 못 했다** — p95
  20~40초는 실사용에 부적합한 수준이다.
- CPU 증설은 "임계점을 높이는 것"이지 "문제를 없애는 것"이 아니다 — 지금
  30 VU에서 버티게 만들었다고 해서 40~50 VU에서도 버틴다는 보장은 없다.
  경로 탐색 자체가 CPU를 많이 쓰는 연산이라는 근본 특성은 그대로다.

### 다음 단계

- 세마포어(S15P21A104-291) 배포 후 3코어+세마포어 조합으로 재측정
- `BE/k8s/prod/be.yaml`의 `limits.cpu`를 실제 운영 값(3000m)으로 맞춰 IaC
  drift 해소
- 근본적인 p95 개선(2초대)은 이번 범위 밖 — 경로 탐색 알고리즘 자체 최적화
  또는 캐싱 확대가 필요한 별도 작업으로 분리

### 교훈

- 리소스 상한을 늘리기 전에, **그 파드가 사는 노드 자체에 여유가 있는지**
  (`kubectl describe node`의 `Allocated resources`)부터 확인해야 다른
  서비스를 굶기지 않고 안전하게 늘릴 수 있다.
- 클러스터에 직접 적용한 변경은 반드시 IaC(YAML)에도 반영해야 한다 —
  안 그러면 다음 자동 배포가 그 변경을 조용히 되돌린다.
- 같은 조건으로 두 번 돌린 결과가 다르게 나오는 건 이상한 게 아니다(JVM
  워밍업 등) — 결과를 해석할 때는 "설정이 진짜 바뀐 효과"와 "그냥 흔들린
  것"을 구분해야 한다.
