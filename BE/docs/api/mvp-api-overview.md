# BE API 전체 목록 (MVP1+2 기준, FE 더블체크용)

기획서(`spec.html`, 2026-08-31)의 MVP1·MVP2 기능과 지금 진행 중인 Jira 티켓(`S15P21A104-6x`)을 맞춰서, **BE가 실제로 명세를 만들어야 하는 API**만 추렸다. FE 리뷰 후 확정되면 각 명세는 Notion으로 옮긴다.

## ✅ 해결된 것 — "역전구간"과 새 기획서의 관계

Jira `S15P21A104-71`(E2E 검증 티켓)의 "경로검색 → 역전구간 판정" 시나리오와 새 기획서(`spec.html`)의 "쾌적/시간 축" 사이에 용어가 안 맞아 보였는데, 논의 결과 정리됐다:

- **"역전구간"** = 지하철 최단경로보다 중간에 다른 수단(따릉이)으로 갈아타는 게 더 빨라지는 구간. 이건 새 기획서의 "혼합 경로 탐색"과 같은 것이다.
- **별도 API를 만들지 않는다.** `search`(`S15P21A104-63`) 하나가 혼합 경로 후보까지 다 포함해서 배열로 반환한다. `S15P21A104-65`는 FE가 부르는 엔드포인트가 아니라, `search`가 내부적으로 쓰는 캐싱 구현(Redis, `S15P21A104-61`에서 만든 것 재사용)으로 정리됐다.
- 이 계산은 AI/데이터 파트가 아니라 **BE 경로 알고리즘(전우석, `ROUTE-002`)**이 한다.

자세한 내용은 [route-api-spec.md](./route-api-spec.md) "배경" 절 참고.

## BE가 명세를 만들어야 하는 API

## BE API가 필요 없는 것

| 기능ID / 항목 | 왜 필요 없나 |
| --- | --- |
| 지도·장소 검색(주소/역 이름 자동완성) | 기획서 6절: FE가 카카오/네이버 지도 API를 **직접 호출**. 우리 BE를 안 거침 |
| F-DA-01 서비스 지역 경계 판정 | 별도 API 대신 `search`(1번) 안에서 범위 밖이면 에러로 처리 예정 — **FE도 이렇게 알고 있으면 되는지 확인 필요** |
| F-DA-02/03/04/08 (탐색 엔진, 비용함수, 혼잡도·소요시간 데이터 적재) | 전부 서버 내부 로직/배치 작업. FE가 직접 부르는 API 아님 |
| F-02-01 정적 턴바이턴 안내 | 1번(`search`)의 `legs` 배열로 이미 커버 — FE 화면 전환/하이라이트는 클라이언트 로직 |
| F-02-10 정상 종료 / F-02-11 임의 중단 | MVP2(정적, GPS 없음) 범위에선 FE가 이미 가진 스텝 리스트로 "마지막 스텝 도달"만 판단하면 됨 — 서버 호출 불필요해 보임. **완료 기록을 서버에 남길 필요가 있다면 얘기가 달라지니 FE 확인 필요** |
| 즐겨찾기 | 기획서 전체(MVP1~5)에 이 기능 자체가 없음 |

## FE 확인 필요

1. `route-api-spec.md`의 열린 질문 1~6 (routeType 값 목록, source 필드, 정렬 기준, 역 이름 포함 여부, 빈 배열 vs 에러, `/api/v1/` 프리픽스 여부)
2. 서비스 지역 판정을 `search` 내부 에러로 처리하는 것에 동의하는지
3. 안내 종료(F-02-10/11) 시 서버에 로그를 남길 필요가 있는지 (필요 없다면 이 두 기능엔 BE API가 아예 없음)
