# 성능 측정 기록 규약

> C 파트(외부 연동·적재·수집기·Kafka)의 "개선 전·후" 수치와 **기준선**을 남기는 자리다.
> 기능 MR에 측정 파일이 함께 실려 오면 리뷰어가 코드와 숫자를 같은 커밋에서 대조할 수 있다.
> 지금까지 남긴 측정은 아래 [기록 목록](#기록-목록)에 있다.

## 원칙

1. **단순한 버전을 먼저 만들고 그 상태를 측정한 뒤 개선한다.** 순진한 구현이 곧 baseline이다. 개선 뒤에 "예전 방식은 아마 느렸을 것"이라고 쓰지 않는다.
2. **예전 경로는 지우지 않고 스위치(환경변수·플래그)로 남긴다.** 스위치만 바꿔 before와 after를 같은 조건에서 다시 측정할 수 있어야 한다.
3. **같은 조건, 여러 번, 분포로 측정한다.** 같은 머신, 같은 데이터 스냅샷, 워밍업 1회 뒤 5회 이상 반복. 평균이 아니라 **중앙값과 p95**를 적는다.
4. **개선율만 쓰지 않고 절대값과 조건을 함께 쓴다.** 행 수, 머신, 도커 자원 제한까지 붙인다. 허수아비 비교(아무도 안 쓰는 방식을 before로 세우기)는 하지 않는다.
5. **개선 대상이 아니어도 규모·처리량은 남긴다.** 신규 적재·수집처럼 before가 없는 작업은 1·2번을 적용할 수 없다. 그래도 "몇 행을 몇 초에"는 기준선으로 적어둔다. 단, **1회 측정치는 1회 측정치라고 쓰고 개선 근거로 인용하지 않는다** — 3번(워밍업 + 5회, median·p95)을 채운 것만 "정식 기록"이다. 조건이 다른 수치끼리(로컬 직결 vs SSH 터널, 커밋이 다른 두 시점) 나란히 놓고 배수를 계산하지 않는다.

## 파일 규칙

- 실험 1건 = 파일 1개. 이름은 `YYYY-MM-DD-<주제>.md` (예: `2026-09-10-edge-time-batch-load.md`).
- 저장소에는 **요약 표만** 커밋한다. psql 출력, probe JSONL, 로그 같은 **원본 출력은 `.claude/perf/raw/`** (Git 제외)에 두고 파일명을 표에 적는다.
- 팀 발표에 쓰는 수치는 Notion에도 옮긴다. 정본은 이 폴더다.

## 기록 항목

| 항목 | 내용 |
| --- | --- |
| 날짜 · 커밋 | 측정한 날짜와 `git rev-parse --short HEAD` |
| 환경 | 머신(CPU·RAM), OS, Docker 자원 제한, PostgreSQL·Redis·Kafka 버전 |
| 데이터 규모 | 행 수, 파일 크기, 호출 건수 등 |
| 조건 | before / after 각각의 스위치 값, 파라미터 |
| 명령 | 재현에 필요한 정확한 명령 |
| 반복 | 워밍업 포함 회수 |
| 결과 | 지표별 min · median · p95 · max |
| 원본 | `.claude/perf/raw/` 안의 파일명 |

### 기준선 — 1회 측정치 (규약 미충족)

신규 적재·수집은 before가 없어 원칙 1·2를 적용할 수 없고, 반복도 안 했다. **규모 감각용이며 개선 근거로 인용하지 않는다.** 다른 조건의 값과 나란히 놓지도 않는다.

공통 환경: 실습실 PC(Core Ultra 9 185H · RAM 63.5 GB) · Docker Desktop · `postgres:16`·`redis:7`·`apache/kafka:4.2.1` 같은 머신 · 적재는 `--load.write-mode=BATCH` 기본. 시간은 로더/수집기 자체 타이머(`elapsedMs`) 로그값.

**실시간 컨슈머** (2026-09-16, 로컬 compose · [consumer.md](../infra/consumer.md))

| 티켓 | 날짜 | 대상 | 건수 | 시간 | 처리량 | 반복 |
| --- | --- | --- | --- | --- | --- | --- |
| 171 | 09-16 | 백로그 따라잡기 (`subway.arrival`) | 50,137 | 60,005 ms | 약 836 건/초 | 1회 · 로컬 — [문서](./2026-09-16-consumer-backlog.md) |
| 171 | 09-16 | **prod 컨슈머 회차 소화** (`subway.arrival`) | 약 3,000/회차 | 5~9 s | 초당 330~600건 | 운영 로그 관측 — [consumer.md 9절](../infra/consumer.md) |
| 171 | 09-16 | **prod produce 구간** (`ingested_at` → 레코드 timestamp) | — | median 41~188 ms | — | 운영 로그 관측 · Kafka 가 얹은 비용 |

- 실부하(초당 약 50건) 대비 약 17배 여유. 보관 48시간치 약 2.9M 건이면 따라잡는 데 **약 58분**.
- 병목은 Kafka 가 아니라 **Redis 순차 왕복**(연산당 약 0.77 ms)이다. 근거와 한계는 문서의 "해석" 절.
- **1회 측정치라 개선 근거로 인용하지 않는다** — 백로그를 소화하면 오프셋이 소진돼 5회 반복하려면 매번 다시 적재해야 한다.
- prod 두 줄은 **설계한 측정이 아니라 운영 로그를 읽은 관측치**다. 로컬(실습실 PC)과 prod(EC2·k3s·1Gi·1CPU)는 조건이 달라 나란히 놓고 배수를 계산하지 않는다.
  다만 자릿수는 맞는다 — 로컬 836건/초 vs prod 330~600건/초.
- prod `consume` 구간(7 ms → 4,500 ms 로 올랐다 리셋)은 **지연이 아니라 회차 소화 진행도**다. 지연으로 인용하지 말 것 (consumer.md 9절).

- `edge_time` 처리량이 70(16,000 행/초) → 113(53,900 행/초)으로 3배 올라 보이지만 **개선이 아니라 측정 구간 차이일 가능성이 크다.** 70의 8.5 s는 prune·환승을 포함한 값일 수 있고 113의 3.6 s는 `edge_time` 구간만이다. 같은 커밋에서 다시 재지 않으면 인용 불가.
- 167(prod)은 SSH 터널을 지나므로 로컬 직결 수치와 **조건이 다르다.** 터널 오버헤드와 로더 성능이 섞여 있다 ([load-prod.md](../db/load-prod.md)).

## 도구

| 대상 | 도구 |
| --- | --- |
| 외부 API 응답 시간·크기 | `node BE/scripts/external/probe.mjs <source> --repeat 5 --jsonl .claude/perf/raw/<파일>.jsonl` |
| 적재 처리량 | 적재 스크립트의 자체 타이머 + `psql`의 `\timing`, 행 수는 `SELECT count(*)` |
| 쿼리 | `EXPLAIN (ANALYZE, BUFFERS)` |
| 어댑터·수집기 지연 | 이벤트의 `source_generated_at` · `ingested_at` · `written_at` 세 시각 차이. Java면 Micrometer 타이머(Actuator 포함) |
| Kafka | `kafka-consumer-groups --describe` 의 LAG, 컨슈머 로그의 중복 제거·덮어쓰기 차단 카운터 |
| 수집기 내보내기 경로 비교 | `PERF=1 PERF_DUMP=<덤프> ./gradlew test --tests '*PublisherBenchmarkIT' -i` — 덤프 재생이라 외부 호출 0회 |
| 테스트 결과 집계 | `node BE/scripts/test-report.mjs [필터]` — 실패한 테스트 이름·메시지를 짝지어 출력 |
| 장애 주입 | 키 무효화 · 오래된 값 주입 · Redis 다운 상태에서 100회 요청, 성공률과 p95 |
